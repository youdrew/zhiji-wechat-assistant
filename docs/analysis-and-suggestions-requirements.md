当前状态：统一开关、逐条后台解读与三候选、消息下默认收起、完整原文复制、局部重试、历史参考、旧开关迁移及媒体读取链路均已接入。当前行为以[分析与建议说明](message-analysis.md)为准；真实建议质量仍需持续评价，见[需求待办清单](requirements-todo.md#validation)。下文的“本轮只整理需求”及未定提案保留原讨论语境，不代表这些主体功能尚未开发。

后续确认（2026-10-13）：展开区改为三条简洁回复和一个“详细解读”入口，背景依据及其他操作收进详情。分析应参考好友背景与截至目标的近 100 条双方聊天；图片和表情贴纸须实际进入视觉读取链路，主动聊天助手同样适用，不得把占位符当作已看图。

将个人聊天中的“聊天分析”和“回复建议”合并为好友姓名右侧的“分析与建议”。开启后，检测到每条好友新消息便自动调用后台 Agent，生成该消息的解读和三条可复制回复。结果默认收起，用户点击消息旁入口时在对应气泡下展开，避免聊天页面堆满分析与候选。

本轮交付独立需求文档和使用虚构聊天的交互演示，不修改应用功能代码。已明确的目标与尚未确认的设计分开记录；本稿不代表交互已经定稿或功能已经实现。

## 已明确的目标

| 事项 | 需求 |
| --- | --- |
| 合并入口 | 入口名为“分析与建议”，位于当前好友姓名右侧 |
| 自动触发 | 开启后，可靠检测到每条好友新消息便自动调用后台 Agent 生成分析与建议，无需用户点击或手动提交问题 |
| 结果单位 | 每条好友消息各有三条回复候选，不将连续几条消息合为只有三条候选的一组 |
| 候选形式 | 三条可直接复制的完整回复，每条独立细边框，框内仅显示正文和复制按钮 |
| 界面目标 | 保留逐条查看能力，同时避免每条消息下都常驻完整分析和三条回复 |
| 展示布局 | 采用已选演示的“消息下展开”，内容出现在对应好友消息气泡下方 |
| 默认状态 | 新消息的分析与建议默认收起；生成完成不自动展开 |
| 查看方式 | 用户点击消息旁入口后展开已生成结果；点击展开不作为新消息生成的触发条件 |
| 当前工作范围 | 先澄清需求并形成独立文档，不开始功能实现 |

“一条消息”按一个好友消息气泡理解，不按标点拆分。一条气泡含多个句子时，仍产生一份分析和三条候选。“逐字分析”是否需要额外提供关键词解释，见待确认事项。

本稿中的“新输入”沿用此前的好友新消息语境，不包括用户在回复输入框或主动助手中编辑的草稿。

## 消息下展开与默认收起

采用用户选定的“消息下展开”方案。每条好友消息旁保留轻量查看入口，分析与三条候选默认都收起；生成完成只更新该消息的可查看状态，不自动展开或拉动聊天列表。沿用所选演示的一次展开一条规则，展开另一条时收起原条，保持阅读位置。

| 用户动作或事件 | 预期行为 |
| --- | --- |
| 开启姓名右侧总开关 | 为好友最近整波未回复消息逐条登记任务，并为后续好友新消息启用后台自动生成；无需逐条点击 |
| 检测到可靠的新消息 | 自动登记并执行该消息的后台 Agent 任务，消息旁显示轻量排队或生成状态 |
| 后台完成生成 | 保存该消息的解读和三条候选并更新标识；未展开的结果继续收起，用户已展开进度的在同一区域更新为结果 |
| 点击已完成消息的入口 | 直接展开该消息已保存的分析与三条回复，不重新请求模型 |
| 点击仍在生成的消息入口 | 展开该任务的进度，完成后在原展开区域显示结果；不重复启动任务 |
| 再次点击当前展开的入口 | 收起该结果，不影响后台任务或已保存内容 |
| 点击另一条消息入口 | 收起当前结果，在另一条消息下展示它自己的状态或结果 |

后台生成与用户查看相互独立。用户一直没有点击消息，也应能在生成完成后直接展开并选择候选。生成失败时仍可提供明确的“重试”操作；手动重试不替代正常的新消息自动生成。

### 展开后的简洁布局

主区仅显示三条简洁回复和一个默认折叠的“详细解读”入口。

- 三条回复各用独立细边框，优先一句自然短句，每条仅显示正文和小复制按钮。
- 原消息保留在上方气泡；主要意思、详细解释、不确定之处与背景依据统一收进“详细解读”，不再分散成多个主区入口。
- 查看旧消息或来源失效时保留一行必要提示；生成失败可简洁重试。
- 重新生成和“继续聊这句”等辅助操作放入详情。带入主动助手时保留已有草稿，由用户主动提交。

2026-10-13 样式确认：聊天区足够宽时三条回复一行展示，空间不足时按实际可用宽度自动换行，不固定为三行。长回复换行完整展示，不裁切成无法展开的正文。

## 自动生成与消息范围

新消息自动调用后台 Agent、每条独立生成、默认收起及主动开启时处理最近整波未回复消息已经确认；历史补充、离线恢复和媒体范围仍沿用以下建议：

自动处理从新消息同步到本机且可可靠读取后开始；聊天同步和生成排队可能带来短暂延迟，不承诺手机端收到消息的同时即有结果。

1. 功能按微信账号和联系人保存，默认关闭，只支持可可靠识别来源和发言人的个人私聊。群聊、服务号、系统消息和用户自己的消息不生成好友解读或三条候选；自己的消息可用于理解上下文。
2. 主动开启时，为好友最近整波尚未回复的消息逐条登记任务，以自己上一条回复为边界；系统消息忽略，遇到无法可靠识别发言人的消息则保守断开波次。每条分别生成解读和三条候选，结果默认收起，不能只处理最后一条。开启后的每条好友新消息继续独立处理，不能因稍后又来一条而漏掉前一条的结果；应用重启不补跑离线积压的规则不变。
3. 每条可靠新消息首次被检测到时立即登记自动任务，重复同步不重复生成。可因模型或执行资源忙而排队，但不人为等待用户点击或连发结束。执行层可以合并调度，不能漏掉任何目标消息或把多条目标合为只有三条候选。
4. 应用运行时，已开启联系人的后台生成不因用户切换聊天或收起展示区而停止；切回时显示该联系人正确的状态。应用退出后不执行。
5. 重启应用或数据源恢复时不自动补跑全部离线积压。历史未生成消息的补充方式，以及是否同时生成三条回顾性回复，仍待确认；展开已有结果本身不得重复生成。
6. 图片、表情贴纸和视频使用实际图像数据生成有限视觉观察，语音沿用已有转写；不可读时明确说明，不能根据媒体占位消息编造内容。动态图片与贴纸仅取首帧，媒体数量和读取范围见[功能说明](message-analysis.md)。

首次开启、历史补充和连续消息的候选必须标明目标原消息；展开另一条已完成消息只读取结果，不重复调用模型。自动任务不要求先打开聊天助手，不读取或写入用户与主动助手的讨论。

每条结果固定其使用的上下文版本，参考截至该条的近 100 条双方聊天与有来源的好友背景，不使用后续消息。记录不足或模型容量有限时明确实际范围，不能声称已读全部历史，也不能把回复后一条的内容误挂到前一条。

## 新消息与阅读位置

新结果默认收起。沿用所选布局的单条展开和阅读位置保护，并保留以下行为：

- 新消息与新结果到来时，不自动展开任何消息，不把较早任务的迟到结果当成最新目标。
- 用户正在查看某条消息、展开依据或选择文本时，新消息不得抢走选中目标、焦点和阅读位置。新消息只更新自己的轻量入口，不自动收起用户正在看的内容。
- 用户已经主动展开仍在生成的消息时，该任务完成后可在同一展开区域更新为结果；这不代表其他消息也自动展开。
- 切换目标时，解读、候选、原消息和状态必须一起切换，不能出现 A 消息的解读配 B 消息的候选。
- 收起结果只影响展示；关闭姓名右侧总开关才停止新的自动生成、取消尚未完成的自动任务并隐藏查看入口。迟到结果不得重新显示，已保存结果保留在本机。
- 切换好友时不展示上一位好友的结果；后台返回也不能切换用户正在查看的联系人。

用户已经回复后，原消息的解读仍有回看价值；针对当时语境的三条候选不能继续被误认为当前推荐。已显示的历史候选仍可直接复制；保留期限与适用性见待确认事项。

## 结果质量与操作边界

每条消息的三条回复应有实际表达或回应方向的差别，不能仅替换同义词。正常闲聊可以自然接话，不强行延伸话题；结合用户表达风格和关系背景，但不预设恋爱或追求目的。

分析区分原文事实、可能解释和不确定判断。不把推测写成对方已经确定的心理，不根据单句给出稳定人格结论，也不作医学判断或人格评分。已确认记忆、待确认资料和用户主观看法应保留各自来源；助手讨论不能成为微信事实。

- 复制由用户主动点击执行，不自动发送微信，不自动填入或覆盖手动草稿。复制成功只反馈到对应候选；失败提供真实提示。
- 复制直接取得点击时显示的候选完整原文，不请求后台核对联系人、目标消息、版本或来源。后台更新不能把本次复制替换为另一条候选；来源未核对、历史参考或需更新状态均不限制复制。
- 自动更新不得修改用户已经输入的文字、选区或光标位置。
- 已完整生成并通过校验的三条候选才能显示为完成；少于三条、空白或重复内容视为生成未完成，不能用预设套话凑齐。
- 结果绑定账号、联系人、目标原消息及所用上下文。模型、来源或人物资料变化时检查适用性，迟到结果不能覆盖新版本。
- 查看、复制或切换已保存结果不触发重新生成。重试和重新生成应有清楚的主动操作入口。
- 分析与候选保存在本机，不写入已确认关系记忆，不混入主动助手历史，不上传到代码仓库。

## 状态与局部失败提案

合并入口不应要求两部分同时成功才能看到任何结果。分析与建议可分别显示状态，但全局不重复堆叠提示。

| 状态 | 建议展示与操作 |
| --- | --- |
| 开启后等待新消息 | 轻量等待状态，无空白三卡或长篇引导 |
| 当前消息排队或生成中 | 消息旁显示轻量状态；未点击时不展开进度卡，已展开时显示该任务的进度 |
| 分析完成而候选生成中或失败 | 保留解读；候选区域显示自己的状态，失败后允许单独重试 |
| 候选完成而分析失败 | 保留有效候选；解读区域提示失败并允许重试，不宣称解读已完成 |
| 两部分完成 | 未展开时继续收起，点击后直接查看；已展开进度时在原区域显示解读和完整三条候选，无需再次生成 |
| 背景、原消息或来源变化 | 标明结果的适用性，不能把旧结果当成当前有效内容；已显示的候选仍可直接复制 |
| 又收到好友新消息 | 自动生成新消息的结果并保持收起；不能因此删除前一条的逐条结果或漏掉其生成，较早候选如何转为历史参考待确认 |
| 用户已经回复 | 原解读可回看；已有候选转为历史参考的规则，以及未完成候选是否继续生成，待确认 |
| 关闭功能 | 停止新的自动生成，取消尚未完成的自动任务并拒绝迟到结果；隐藏入口，保留已保存结果和手动草稿 |

多条消息排队时不能无限重试同一失败任务；生成速度落后于消息到达速度时，界面需明确积压状态，不能通过跳过部分目标消息减少任务。可考虑暂停继续生成、保留未完成目标并提供恢复入口，具体策略待确认。

“当前可用”“历史参考”“需更新”应是可区分的状态。每条已生成结果分别保存，已显示的候选均可主动复制；历史候选的保留期限是独立决定，适用性提示不限制复制。

## 旧开关与已有数据

现有“聊天分析”和“自动建议”有都关闭、仅分析、仅建议、都开启四种组合。迁移规则待定，不能简单把任意旧开关开启解释为同意新增另一类自动生成。

建议升级时保留原设置和已有数据；对只开启一种能力的联系人，由用户首次主动开启合并功能后再启用两种自动生成。两者都开启时可映射为合并开启，但由于候选从“每轮三条”变为“每条三条”，生成范围变化仍需说明。旧状态如何在单一入口中表达，需在实施前形成完整迁移表。

旧逐条分析可以继续回看。旧回复候选未按每条消息保存的部分不能伪装成逐条历史结果，也不能为迁移而自动批量补生成。

“消息下展开”“后台自动生成”“默认收起、点击查看”“每条各三条”和“独立细框内的完整可复制回复”已明确，不再作为待选项。其他建议不因布局选定而自动升级为已确认要求。

## 验收场景草案

1. 好友姓名右侧只有一个“分析与建议”入口；合并后的页面不再出现两套互相矛盾的开关。
2. 开启功能后，好友连续发送三条消息，用户不点击任何消息，后台也为每条分别生成分析与三条完整候选。生成完成后页面仍默认收起，不铺开九条回复。
3. 点击已完成消息可立即在原消息下查看保存的结果，不再调用模型；点选另一条消息时，原文、解读、三条回复和状态始终对应同一目标。
4. 每条候选都有短标签、可读完整正文和独立复制操作；点击后直接复制所见原文，不请求后台核对，不受来源或历史状态限制。复制或新结果不会改变手动草稿。
5. 用户查看某条消息时又有新消息到来，当前阅读内容不跳走；新消息自动生成但保持收起，用户可主动查看它。
6. 分析或候选单独失败时，另一部分仍能使用；重试不重复添加结果，也不恢复已经失效的旧版本。
7. 切换联系人、账号、模型或来源后，后台迟到结果不会串到另一目标；关闭功能后不产生新的自动任务，原未完成任务也不能恢复显示结果。
8. 用户已回复后，旧分析与旧候选按最终的历史规则展示，不将历史话术当成当前建议。
9. 应用重启不批量补跑全部历史；后台好友范围、媒体和群聊行为符合最终确认的触发范围。
10. 小窗口、长原文、长候选及打开聊天助手时，文字和操作仍可用，没有遮挡或无法展开的截断。
11. 四种旧开关组合都可按迁移表升级，原有数据不被清除，也不静默启用用户原先关闭的能力。
12. 连续消息生成积压时，每条目标仍有可追踪状态；不会退化为只保留最新消息，恢复后遵守确认的上下文与历史规则。
13. 点击仍在生成的消息只展示既有任务进度，不重复启动请求；用户编辑主聊天或主动助手草稿也不触发好友消息分析。
14. 好友已连续发来 10 条消息、用户尚未回复，再开启功能时，应将这 10 条逐条登记，各自生成解读和三条完整候选，全部结果默认收起；不得只处理第 10 条，也不得越过用户上一条回复或发言人不可靠的消息补跑更早消息。期间的系统消息不算好友消息，也不截断这波未回复消息。
15. 展开正常完成的结果时，主区只有三条紧凑回复及“详细解读”；背景与辅助操作在详情内，复制、草稿、选区及阅读位置保护保持有效。
16. 分析与候选请求均包含截至目标的近 100 条聊天及可用好友资料；前文的有限媒体观察随消息进入上下文。合成图片和表情通过实际视觉读取，读取失败明确标记，不能假装看过。

主要交互与主动开启范围已确认；历史候选与迁移等剩余规则补齐后，作为功能实施与验收基线。此前讨论阶段只整理需求，不修改应用功能代码；后续实施授权见文首记录。
