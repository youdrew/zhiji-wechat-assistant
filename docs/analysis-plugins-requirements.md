现有默认方案的分析规则见[知己分析 v2 需求](friend-analysis-v2-requirements.md)；本稿讨论其可替换边界，不因插件化自动改变该方案已确认的分析口径。

## 1. 目标与范围

重新划分软件核心，将全部增强功能作为插件承载。核心最重要的职责是维护进入本软件的微信聊天数据，同时提供统一模型调用、路由和监控。核心应保持稳定，不包含 AI 分析业务，也不定义插件怎样使用模型；分析、助手、建议等 AI 业务由插件决定。本稿保留已确认的分析方案交互，并逐步补齐其他功能的插件边界。

**用户明确扩大为全部增强功能插件化，重新划分软件核心。** 这取代 v0.1–v0.2 的“仅知己分析方案插件化”限制。微信接入以及外部导入的入口、核对和保存保留内置，核心保管已保存的联系人、聊天记录和人工资料；外部导入的 AI 识别流程由默认附带的导入插件负责。

**软件默认携带用户自己制作的一组插件；所有插件的模型调用统一经过 core 的模型路由。** 预装表明交付时可用，不表示将其分析业务重新放回核心。**已确认：目前插件均由用户自己编写，未来允许他人编写插件；插件安全由使用者自行负责，Core 不做权限隔离、签名审核或沙箱。** 首版是否支持独立安装、替换和单独更新，以及具体分发方式，尚未确认。

知己分析仍需让同一位好友采用不同方法并随时切换。现有分析作为其中一个方案插件，未来方案可以有不同的分析过程和展示栏目。扩大范围不撤销每好友选择方案、结果分别保留和导入与分析解耦等已确认决定。

## 2. 已确认的产品决定

| 事项 | 已确认方向 |
| --- | --- |
| 总体范围 | 全部增强功能插件化，重新划分软件核心 |
| 内置能力 | 微信接入以及外部导入的入口、核对和保存内置；核心保管已保存的联系人、聊天记录和人工资料 |
| 导入插件 | 外部素材的 AI 识别由默认附带的导入插件负责，遵守统一模型路由；与后续人物分析独立 |
| 核心首要职责 | 维护微信聊天数据到本软件，核心需要保持稳定 |
| 统一基础设施 | 模型调用、模型路由和监控属于核心；所有外部插件使用同一套 core 模型路由 |
| AI 业务边界 | 核心不含 AI 分析功能，不定义模型怎样被使用；AI 分析业务由插件提供 |
| 默认交付 | 软件默认携带用户自己制作的一组插件；具体清单和初始启用规则待定 |
| 故障隔离目标 | 插件出错或卡住，不能影响核心维护聊天数据，也不能无限阻塞其他插件 |
| 已确认的运行模式 | 按插件独立后台进程、插件界面运行隔离；Core 分开执行数据维护、模型网关、监督和监控职责，统一管控资料访问、资源排队与任务生命周期 |
| 停止与恢复原则 | Core 撤销旧任务提交资格，协作取消超时后可独立结束插件；保留已提交结果，迟到结果不能写入新任务；重启后未完成业务由用户继续 |
| 全局模型调用入口 | 左侧导航栏独立“模型调用”按钮，放在设置上方，打开模型调用面板 |
| 全局监控范围 | 展示所有好友的调用数据，支持按好友筛选 token 用量；不再以当前好友作为面板的默认范围 |
| 基础用量与完整诊断 | 常记调用归属、状态、耗时和 token；完整提示词与回复按需采集，由开发者模式单独控制 |
| 增强能力 | 分析、助手、建议等功能作为插件；现有默认知己分析成为一个方案插件 |
| 选择范围 | 每位好友选择一个当前方案，不强制所有好友使用同一种方法 |
| 切换 | 随时可以切换当前方案，各方案结果分别保留、互不覆盖 |
| 分析过程 | 方案可以定义自己的分析步骤，不强制沿用现有六步流程 |
| 展示栏目 | 方案可以定义自己的栏目或页面，不强制复制现有五个页签 |
| 宿主能力 | 提供统一的任务进度、停止操作和原文证据查看 |
| 与导入解耦 | 分析模块读取已保存的聊天资料；导入只保存外部记录与可选备注，不启动分析方案任务 |
| 主聊天入口精简 | 移除旧“意图识别”和“重置会话分析”按钮，减少重复入口 |
| 功能独立性 | 主动聊天助手和“分析与建议”继续独立存在，其插件边界纳入本次讨论 |
| 插件作者与安全责任 | 目前插件均由用户自己编写，未来允许他人编写；插件安全由使用者自行负责。Core 只做故障隔离，不做权限隔离、签名审核或沙箱 |
| 模型网关形态 | Core 为每个已配置的模型服务提供本机标准协议接口；插件持短期令牌按该服务协议调用，凭据由网关注入，不交给插件 |
| 切换时的旧任务 | 切换只改变查看对象，原方案任务继续在后台运行并有提示；仅当在新方案开始分析而原任务仍在运行时，才询问停止原任务或排在其后 |

切换当前方案表示选择该好友正在查看和准备使用的方法；**不表示删除其他方案结果，也不表示同时启动全部方案**。

**已确认切换时旧任务的处理：** 切换方案不停止、不暂停原方案正在执行的任务；原任务继续在后台运行，窗口标示“方案甲仍在后台分析”，用户可切回查看进度或手动停止。只有在新方案上点击“开始分析”且原方案任务仍在运行时，才提示“停止方案甲”或“排在它后面”：选择停止则按停止原则结束原任务、保留已提交结果后启动新任务；选择排队则新任务显示“排队中”，原任务结束（完成、失败或停止）后再启动。由此同一好友同一时间最多一个分析方案在执行；切换和查看本身绝不悄悄启动新方案。应用重启后排队任务不自动启动，按已确认的停止与恢复原则由用户继续；关闭窗口或切换账号时排队任务如何处理，随任务生命周期契约细化。

### 统一模型路由与业务流程的边界

已确认原则是所有插件共用 core 的模型路由，core 不承载分析方法。以下是接口职责的细化建议，不是已冻结的接口规范：

| core 提供的通用机制 | 插件决定的业务策略 |
| --- | --- |
| 按用户配置核对模型与能力、连接服务、管理凭据及处理协议差异 | 为任务选择所需能力，组织提示词、输入内容和生成参数 |
| 查询资料、返回来源与版本，校验允许读取的范围 | 本轮读取哪些资料、如何分段、何时总结或压缩上下文 |
| 经本机标准协议接口转发模型请求、传递流式结果、报告用量与技术错误 | 选用何种 SDK 或 Agent 引擎；是否需要多轮调用、Agent 工具循环、输出解释与分析规则 |
| 提供可追踪的请求标识、取消、技术超时、资源限制及明确的重试记录 | 对答案不完整或不合要求的业务重试，以及下一步调用方式 |
| 汇总插件、任务、模型调用的状态、耗时、用量和错误 | 声明任务名称、步骤及业务完成情况，解释分析结果 |

**已确认网关形态：本机标准协议接口。** Core 不另设一套自定义的“生成”调用格式，而是为每个用户已配置的模型服务提供一个本机接口，沿用该服务原有的协议格式（以现有连接器支持的 Anthropic、OpenAI Responses、Chat Completions、Gemini、Ollama 为准）。插件或其使用的 SDK、Agent 引擎（如 opencode）只需把请求地址指向该本机接口，并携带 Core 签发的短期令牌：

- 令牌绑定插件、插件版本、任务、执行实例（代次）及允许的账号／好友范围；网关据此记录调用归属，不依赖插件自报。
- 真实凭据由网关在转发时注入，不写入插件配置、环境变量或日志。
- 网关核对请求的模型与用户配置一致，不接受插件自行指定未配置的服务；排队、并发限制、技术重试、取消和计量都在网关执行。
- 停止任务时作废该执行实例的令牌，即为停止流程第 1 步在模型请求侧的实现；作废后的新请求一律拒绝。
- 网关需理解各协议到足以计量用量、取消请求和转发流式结果的程度；首版不要求在不同协议之间互相转换（建议）。
- 为简化插件代码可提供插件侧的辅助库，但它属于插件开发工具，不进入 Core。

由于 Core 不做权限隔离，“所有模型调用经 Core 路由”是插件契约要求，而非技术强制；插件若自行直连模型服务，其调用不在监控和计量范围内，责任在插件作者。现有军师已通过本机转发服务（`ModelTraceRelay`）连接 opencode，可作为网关的起点；但目前 API key 仍写入 opencode 的配置，迁移时需改为由网关注入（[electron/runtime.ts:298](../plugins/kyf.advisor/engine/runtime.ts)、[同文件:501](../plugins/kyf.advisor/engine/runtime.ts)）。

core 的容量检查应返回限制或失败原因，不自动选掉聊天片段或生成摘要。core 的技术重试应有边界并可观察，插件重试也需登记，避免两层无界叠加；模型切换和回退应遵守明确配置，不暗中替换会改变结果含义的模型。具体重试及路由规则尚待讨论。

已确认的导入链路为：内置导入入口接收素材 → 默认导入插件通过 core 路由执行 AI 识别 → 返回待核对记录 → 内置界面核对并确认保存。正式记录由核心管理；后续分析独立读取，不因识别或保存完成自动启动。建议插件不可用时说明识别暂不可用，仍可浏览已保存资料；具体失败恢复和替换行为待定。

建议每次调用都能关联插件、插件版本、任务、步骤和请求；实际调用的模型及技术重试可回查。监控缺少用量时显示未知或估算，不编造数值。凭据不交给插件或写入日志；聊天内容与完整提示词的监控留存范围另行定义，不因“统一监控”自动扩大。

### 核心稳定性的可验证目标

- 插件加载失败或分析执行失败时，微信数据维护、聊天浏览和其他插件仍可使用；独立运行模式已确认，具体进程 API 与资源参数待设计。
- 插件的模型请求有统一排队和资源限制，某个插件持续请求不能无限占用所有执行资源。
- 停用或取消后拒绝旧任务的迟到写入；部分结果、故障记录和已保存资料有明确状态，不能伪装成完整成功。
- 插件通过有版本的接口读取和保存资料，不直接修改核心数据库结构；不兼容的插件可被阻止加载并显示原因。
- 默认携带的插件也通过相同接口和模型路由执行，核心不为它们保留隐含的分析调用路径。

用户已认可上述架构模式，具体故障注入、指标和验收条件仍需细化，不代表隔离、调度或兼容机制已经实现。现有代码中用于总结、画像、上下文压缩或 Agent 编排的业务，需要逐项辨认归属，不能仅因目前位于共用服务里就算作核心能力。

### 插件运行隔离方案（模式已确认，详细设计待评审）

用户已确认故障不能影响核心聊天数据维护或拖住其他插件，并同意本轮介绍的架构模式：按插件独立运行，Core 统一管理数据访问、模型排队和任务生命周期，界面运行也需隔离。下文将模式展开为设计约束；具体协议、运行 API、资源限额和兼容策略仍待评审，不因总体同意而自动定稿。

**以插件为后台故障隔离单位，按需启动独立进程。** 同一插件可以处理多个好友的任务，不按好友创建常驻进程；同一插件进程被强制结束时，其在途任务都可能中断。需要更细隔离的重任务以后可使用受限的任务工作进程，不默认无限增加进程。

core 是职责边界，不要求全部功能处于一个进程。按已确认模式，将微信数据维护、模型请求执行、插件监督和监控存储分开执行；具体进程拓扑和接口如下表所述，需由详细设计验证：

| 运行部分 | 主要规则 |
| --- | --- |
| 核心资料服务 | 微信维护不等待插件结果；保存和查询原文，通过有界接口向插件提供资料 |
| 插件监督器 | 负责启动、健康检查、停止和回收插件进程，不执行插件业务代码 |
| 各插件工作进程 | 各自执行提示词、Agent 流程及结果解析，故障不终止其他插件进程 |
| 核心模型网关 | 以本机标准协议接口接收插件请求，在独立于数据维护的执行边界进行连接、排队和请求管理；模型服务无响应不阻塞数据维护 |
| 插件界面 | 受控组件描述由宿主渲染；若运行插件自己的界面脚本，则使用独立的界面运行边界，不注入主聊天执行环境 |
| 核心监控记录服务 | 有界异步采集与独立存储；列表统计和正文查看不占用聊天入库事务 |

**进程独立还需要共用资源的限制。** 插件读取历史采用分页和数量上限；不能获得核心数据库连接、任意 SQL 或跨请求事务。插件计算、模型等待和页面渲染都不能发生在核心数据库锁内。插件结果按插件与任务隔离保存；原文维护和大批结果保存应有独立队列和短事务。通信消息、进度频率、队列长度、CPU、内存及临时文件也需设限，具体数值通过实测确定。

模型网关按端点／资源池管理容量，并行数量由核心的“模型设置”统一配置，所有插件共享额度；插件仍有等待队列上限以限制大量提交，在插件之间公平分配执行机会。同一插件内再按业务顺序调度任务；主动交互可以优先，但后台任务应能随等待获得机会。故障端点的请求、重试和退避不能占住其他端点的执行队列。插件不能通过大量提交请求绕过核心的模型并发限制。

共享模型容量有限时允许正常排队。“不拖住”表示故障不传播、请求不无限占位且调度公平，不表示单并发模型能够同时服务所有插件。请求结束期限、流式空闲期限、排队上限分别设定；远端调用已发出后不承诺可瞬时抢占。

**健康检查区分进程存活和任务进展。** 插件心跳正常不证明任务有进展；合法地等待模型也不等于插件卡死。core 结合执行状态、请求期限与进程响应判定“排队”“等待模型”“运行中”“无响应”，超出边界后显示真实原因，不统一标为失败。

停止原则已确认，具体执行顺序供接口与事务设计评审：

1. core 先使任务和执行实例的提交资格失效，拒绝后续模型请求与结果写入，再发送协作取消通知。
2. 从队列撤出未发出的请求，对已发出请求尝试取消；本地停止采用结果。远端是否停止计算可能未知，已发生的用量仍应归入原调用。
3. 清理超过限定时间后，监督器终止该插件进程及其受管子进程，其他插件和数据维护继续运行。
4. 保留已正式提交的结果与检查点；未提交的中间结果不作为完成报告发布。事务提交时复核执行代次、任务状态和资料版本，重复或迟到提交不得覆盖新任务。
5. 重新启动使用新的执行实例，未完成业务默认显示“已中断，可继续”，不自动重跑所有模型请求。是否允许一次自动重启容器另定，禁止无界崩溃重启。

监控发生拥塞或写入失败时，不能反向等待聊天数据维护或模型传输。采集使用有界缓冲，无法持久化的范围明确标为缺口，不能宣称统计完整；断电或磁盘故障下也不承诺无损计量。取消后到达的有效用量可以更新原调用账目，但不能恢复旧业务任务或写入分析结果。

**已确认这些机制只用于故障隔离，不作为安全边界。** 插件以当前 Windows 用户身份运行，可以自行访问网络和本机文件；单独创建进程不限制其系统权限。未来他人编写的插件同样如此：Core 不提供权限隔离、签名审核或沙箱，安装和使用他人插件的安全风险由使用者自行负责。Core 接口上的账号、好友范围校验用于防止插件错误读取或串写资料（正确性），不承诺阻止恶意插件。

技术依据：Electron 官方说明独立渲染进程与后台 utility process 的用途，可作为界面和后台隔离的候选基础（[Process Model](https://www.electronjs.org/docs/latest/tutorial/process-model)）；Windows Job Objects 可管理进程组、限制部分资源并终止受管进程组，可作为本机资源管理候选（[Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)）。最终进程 API、插件语言和限额尚未选型；需要验证实际进程树、共享资源与故障恢复行为。

### 全局模型调用面板

已实现：入口位于左侧导航栏、设置按钮上方，打开独立模型调用窗口，默认查看当前账号全部好友的调用数据，并可按好友筛选 token 用量。旧的聊天头部入口和默认跟随当前好友的设计已退役，见[开发者模式当前实现](developer-mode.md)。

建议入口常驻，无须选中好友或开启完整诊断才能查看已保存用量。切换主聊天不改变面板筛选。“所有好友”指当前有权查看的资料范围，不自动扩大为所有微信账号；切账号仍撤销旧读取，具体跨来源资料范围随核心身份方案确定。面板在主内容区还是复用已有独立窗口待定，本轮不把“全局入口”等同于某一种窗口形式。

建议布局：

- 顶部筛选：时间、好友（全部／指定好友／未关联好友／多好友任务）、插件、模型及状态。
- 汇总：实际请求数、已知输入与输出 token、总用量、缺少用量的请求数；估算用量单独标明。
- “按好友汇总”：好友、请求数、输入 token、输出 token、已知总用量、失败次数、最近调用；可按用量排序，点击好友进入其明细。
- “调用记录”：逐次展示时间、好友或范围、插件、实际模型、状态、token 和耗时，复用现有任务链及请求／响应详情。
- 汇总覆盖筛选范围全部记录，由后端聚合，不通过相加当前分页数据计算。查看、筛选和切换页签均不发起模型请求。

**已确认基础用量常开，详细诊断按需采集。** 基础记录保存调用归属、状态、耗时和 token，不因开发者模式关闭而停止；完整提示词和回复由开发者模式单独控制。建议两类记录的保留和清理分别定义，清理正文不清空 token 统计；具体保留期限和清理入口待定。升级前未记录、服务未返回用量或采集故障形成的未知范围必须可见，不能补成零。诊断与全局面板的需求衔接见[开发者模式需求](developer-mode-requirements.md)，当前实现见[开发者模式说明](developer-mode.md)。

建议的统计口径：

| 情况 | 记录方式 |
| --- | --- |
| 归属 | core 绑定插件和版本、账号／好友范围、任务、执行、步骤及实际尝试；不依赖查看时选中的好友 |
| 重试和兼容回退 | 每次实际模型尝试单独计数；失败或结果被丢弃但服务返回用量的，仍计入消耗 |
| 流式返回 | 同一次尝试按唯一标识更新累计快照，不逐片段重复相加 |
| 缓存 | 应用复用已有结果不产生新模型用量；服务端缓存按协议含义展示，已包含在输入中的部分不再次相加 |
| reasoning 及总量 | 由 core 根据协议归一化并保留原值；不把已包含在输出中的 reasoning 重复加到总量 |
| 缺少用量 | 显示未知，合计注明“已知用量，另有 N 次未提供”；估算与服务报告分开 |
| 无好友或多好友 | 应用级调用保留独立归属；跨好友请求全局只计一次，无可靠分摊依据时归“多好友任务”，不向每人重复计全量 |
| 时间 | 建议按实际尝试开始时间归属日期，采用客户端时区；跨日流式更新不重复计数 |
| 取消和迟到响应 | 账目仍归原尝试；请求状态、业务是否采用及计量完整性分别显示 |

### 资料与功能组织（建议）

关联的[外部导入需求](external-chat-import-requirements.md)已明确：外部记录归到好友名下，按来源分别查看，可以新建没有微信的好友。本稿据此设计共享资料接口；好友标识、来源账号／会话映射、跨平台关联和关联错误的拆分仍需细化。建议不凭同名自动合并，不自动跨账号开放资料。解除来源连接、停用增强插件和删除资料应是不同操作；已保存的外部记录不因微信账号切换或清除而被连带删除。仅引用外部文件的媒体仍可能因原文件缺失而不可用；已确认留存的导入素材按导入需求管理。

建议插件通过核心提供的资料与明确能力接口协作，避免直接读取另一插件的数据库或调用其内部模块。例如，回复建议通过核心读取已确认记忆，无须安装知己分析；知己分析提出的候选在确认前仍是该方案的待确认内容。旧的未确认候选共享规则需要明确来源、有效性及停用后的行为，不能在拆分时无意改变。

建议按能独立启停、替换的完整用户功能划分插件。知己分析的概述、人格、趋势等栏目先由方案自行组织，不因为栏目不同就拆成互相依赖的小插件。页面扩展允许不同方案有不同交互，公共进度、停止和证据回查保持一致。

插件私有的中间结果与可长期查看的报告需要区分。建议核心保留带版本、输入范围、原文引用的可读报告快照；停用或卸载插件后，基本报告仍可查看，专用交互可标为不可用。此能力需要明确保存格式，不能仅靠保留插件私有数据实现。

本轮先讨论核心职责，再讨论插件的自由度、功能之间的组合、启停与升级，最后讨论迁移。全部增强功能可插件化是目标，尚不表示一次性重写或立即开放第三方代码执行。

## 3. 分析方案交互草案

以下为待审阅的交互建议，不是已确认的具体布局。

1. 主聊天保留“知己分析”入口，打开当前好友的分析窗口。
2. 窗口顶部显示好友名称和“分析方案”选择器，展示当前方案名称及简短说明。
3. 选中已有结果的方案，直接展示其保存结果，同时说明覆盖范围、生成时间和是否待更新。
4. 选中未分析过的方案，显示方案简介、预估和“开始分析”；不因切换而立即全量扫描。
5. 运行时由宿主显示真实进度和“停止”。方案提供自己的步骤名称及完成状态，停止后保留已可靠保存的内容。切换到其他方案时原任务继续在后台运行，窗口标示“方案甲仍在后台分析”；在新方案点击“开始分析”而原任务仍在运行时，提示“停止方案甲”或“排在它后面”（已确认，见第 2 节）。
6. 栏目随所选方案变化；“查看原文”使用宿主提供的同一证据查看入口。
7. “重新分析”放在知己分析窗口中，明确作用于当前方案；完成前保留上一份可用结果。

已确认软件携带用户制作的默认插件。建议现有知己分析作为其中一个，已有好友沿用它作为初始当前方案，避免升级后找不到原有结果。具体预装清单、启用规则、迁移与初始选择仍待确认。

## 4. 分析场景中宿主与方案的最小边界（建议）

| 宿主负责 | 方案插件负责 |
| --- | --- |
| 核对好友、账号、会话及资料范围 | 声明方案身份、版本、适用条件和需要的资料 |
| 提供授权的原文、消息身份和来源回查 | 定义分析方法、步骤、指标和生成规则 |
| 提供已有模型连接、执行资源和任务状态 | 提供预估、进度及方案自己的分析结果 |
| 执行停止、恢复、版本核对和受控保存 | 定义自己的栏目、页面及证据引用 |
| 保存和管理人工资料、确认资料及原文 | 保存方案自己的候选、推测、报告和检查点 |

建议用户确认的记忆、人工观察、联系目标及自身资料由宿主管理，切换方案不复制或清空。方案提出的记忆候选保留方案来源，由既有确认流程处理；报告中的推测不能直接进入已确认资料。

建议原文证据使用共享定位方式，报告与检查点按“好友＋方案＋版本”隔离。不同方案可以引用同一条原文，不得互相修改对方结果。查看原文、旧报告或切换方案不调用模型。

输入建议保留来源、消息顺序、时间是否已知及资料完整性，以便未来使用外部导入的聊天。缺少日期不补造时间；需要准确时间的指标说明不可计算，其他可用分析不必全部停用。具体输入结构不在本稿中定死。

**已确认：导入与分析分别作为两块功能。** 分析方案通过软件的聊天资料读取能力消费已有记录；导入任务不依赖当前方案，不调用方案执行入口。分析范围、触发和更新策略属于分析模块自己的需求，不能作为导入完成后的附带动作。

外部记录备注是用户说明，不是发送者原话。建议与正文分开传递来源类型；分析是否需要使用备注及怎样展示其归属，在分析模块中定义。资料变化可以使结果标为待更新，但不能由导入模块为此直接启动重算。

宿主复用当前模型设置和受控业务接口。Core 接口本身不提供任意文件、命令或微信发送能力；插件自身的系统访问不受 Core 限制，安全责任按已确认原则由使用者承担（见运行隔离方案）。分发方式另行讨论。

## 5. 两个旧按钮的退役边界

已接受的产品方向是移除主聊天的“意图识别”和“重置会话分析”按钮。以下是实施前应审查的建议，**不是删除所有意图分析算法、共享模型代码或历史数据的授权**。

- 旧意图识别开关会驱动消息标签显示及后台请求。建议检查并退役不再使用的触发路径，避免隐藏按钮后仍重复分析；保留真正被其他能力需要的依赖。
- 当前知己分析也会按消息块分析意图、情绪和回应方式。这些属于所选方案的方法，与移除旧按钮是两件事。
- 旧重置操作清理旧消息标签和画像；新方案的“重新分析”应针对当前方案，不借用旧清理操作删除其他方案或用户资料。
- 主动助手、“分析与建议”及其已保存结果不因本次入口精简而停用或清空。旧画像和标签如何保留、只读回看或退役，需依赖审查后确定。
