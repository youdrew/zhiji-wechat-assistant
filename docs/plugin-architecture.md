## 1. 进程拓扑

| 运行部分 | 进程 | 职责 |
| --- | --- | --- |
| 桌面外壳 | Electron 主进程 | 主窗口、分析窗口、插件页面视图、模型调用窗口及受限 IPC |
| Core 资料服务 | Python `bridge/`（本机回环 HTTP） | 微信资料维护、聊天浏览、人工资料、任务生命周期、插件管理与监督、插件资料接口、事件分发、用量账本与诊断记录 |
| Core 模型网关 | `bridge/core_gateway.py` 启动 `scripts/model-gateway.ts`；实现位于 `electron/model-gateway*.ts` | 为已配置的模型服务开放本机标准协议接口，校验执行令牌、注入凭据、排队、计量与取消 |
| 插件 | 每个插件一个独立进程组 | 分析方法、提示词、上下文取舍、Agent 流程及插件自己的资料 |
| MCP stdio 适配器（2026-10-27） | 由本机 AI 客户端启动的独立 Python 进程 `scripts/mcp-stdio-adapter.py` | 按需复用/拉起同一安装的无界面 Core，经回环 `/api/mcp/*` 专用认证路由访问 Core 能力代理；stdout 只写 MCP 消息，诊断走 stderr。授权与权限判断全部在 Core（`bridge/core_mcp_*`），适配器只是协议转换。高影响删除的确认窗（`scripts/confirm-window.cjs`）与后台发送执行器是按需拉起的独立组件，各持自己的租约。见 [MCP 插件实施方案](mcp-plugin-implementation.md) 与[使用说明](mcp-plugin-guide.md) |

- 插件进程组由 Core 监督器启动，加入 Windows Job Object：插件结束或被强停时，其子进程（例如 Node 模型工作进程、opencode）一并回收；Core 退出时整组关闭。
- 插件崩溃、卡死或超时只影响该插件的任务；微信资料维护、聊天浏览和其他插件继续运行。
- 这些机制只用于故障隔离，不是安全边界：插件以当前 Windows 用户身份运行，可以访问网络与文件；安全责任由使用者承担。

## 2. 插件包与清单

插件是一个目录，根目录有 `plugin.json`：

```json
{
  "schema": 1,
  "id": "kyf.friend-analysis",
  "name": "知己分析",
  "version": "0.1.0",
  "description": "按好友分析近期概述、关系记忆候选、人格倾向、聊天互动与关系趋势",
  "core": { "api": [1] },
  "runtime": { "type": "python", "entry": "backend/main.py" },
  "events": ["friend.opened", "human.changed"],
  "contributes": {
    "chatHeader": [{ "id": "analysis", "label": "知己分析", "kind": "friend-window" }],
    "schemes": [{ "id": "default", "name": "默认方案", "summary": "…",
      "page": "ui/index.html",
      "tabs": [{ "id": "overview", "title": "好友概述" }, { "host": "memories" },
               { "id": "persona", "title": "人格分析" }, { "id": "chat", "title": "聊天分析" },
               { "id": "trend", "title": "关系趋势" }] }]
  }
}
```

| 字段 | 规则 |
| --- | --- |
| `id` | 小写字母、数字、点和连字符，3–64 字符，全局唯一；内置插件使用 `kyf.` 前缀 |
| `version` | 语义化版本 `主.次.修订` |
| `distribution` | 可选：`bundled` 或 `external`。`external` 表示外部插件，即使放在 `plugins/` 也显示为“外部”、新安装默认停用；省略时沿用发现目录的默认规则 |
| `dependencies` | 可选：最多 32 个互不重复的依赖插件 ID，JSON 数组，例如 `["example.plugin-b", "example.plugin-c"]`；不得依赖自身，省略时为 `[]`。只声明硬依赖，不声明插件版本范围 |
| `core.api` | 插件兼容的 Core 接口主版本列表；当前 Core 提供 1。不兼容时不加载并显示原因 |
| `runtime` | `python`（Core 自带 Python，隔离模式运行）、`node`（Core 自带 Node 与 tsx）或 `command`（插件目录内可执行文件） |
| `events` | 插件关心的事件类型，见第 6 节 |
| `contributes` | 界面扩展：`schemes`（分析方案）、`chatHeader`（聊天标题旁开关或独立分析窗口入口）、`messageAnnotations`（消息旁标注与建议）、`chatToolbar`（输入区按钮与右侧面板）、`nav`（左侧导航页面；`icon` 可选宿主图标 `assistant`，其他值显示通用图标）、`settings`（插件默认设置，由宿主统一呈现） |

插件版本约定（2026-10-14 用户确认）：三个内置插件统一从插件化后的首个开发版本 `0.1.0` 开始，各自独立升级；只升级实际发生变化的插件。

- 开发期修复问题递增修订号，例如 `0.1.0 → 0.1.1`；新增功能或调整开发期接口递增次版本，例如 `0.1.x → 0.2.0`。
- 接口稳定、完成验收并正式发布时升到 `1.0.0`。正式版之后，修复问题递增修订号，兼容的新功能递增次版本，不兼容的变更递增主版本。
- 应用版本、需求迭代号（如“知己分析 v2”）、提示词规则及摘要缓存版本分别维护，不作为插件 `version` 的编号依据。清单 `schema` 和 `core.api` 也按各自契约维护。

来源与启停：

- 插件放在安装目录 `plugins/`，可随主程序附带，也可手动复制完整插件目录到这里安装。未声明外部分发的插件默认启用；清单声明 `"distribution": "external"` 的插件显示“外部”，新安装默认停用，需要在“设置 → 插件”中启用。
- 本机开发插件仍可放在 `.local/plugins/<目录>/plugin.json`，默认停用，界面也显示“外部”；本机目录不能通过声明 `bundled` 获得内置插件的启用默认值。
- 同一 `id` 出现在两个目录时，`.local/plugins` 不覆盖 `plugins/` 中已发现的插件，显示重复提示。
- 启停状态保存在 `.local/core/plugins.json`。停用插件会停止其任务和进程，保留其资料；重新启用后继续使用。
- 默认启停值只在该插件尚无已保存的启停选择时使用；声明改成外部后，已有明确的启用或停用选择仍保留。
- `chatHeader` 中 `kind: "friend-window"` 由主窗口插件槽呈现，位置在“聊天记录”左侧，打开当前联系人的独立分析窗口。“知己分析”插件提供此入口；停用、移除或不兼容时撤下按钮，重新启用时立即恢复。群聊隐藏，未选择联系人或聊天资料未就绪时禁用。

### 插件之间的依赖

2026-10-23 起，插件可在 `plugin.json` 中声明 `dependencies`，例如 A 的依赖项为 `["example.plugin-b", "example.plugin-c"]`。Core 启动 A 前检查完整的传递依赖图；B、C 及其依赖必须已安装、兼容并由用户启用，且不存在循环。Core 先启动依赖并等待每个依赖进程发出 `ready`，再启动 A；缺失、停用、不兼容、循环或依赖启动失败都会阻止 A 启动。旧清单可省略该字段，原有独立启动行为保留。

- 依赖插件需要在“设置 → 插件”中手动启用；启用 A 不会自动启用 B、C，也不会改变外部插件默认停用的规则。
- `enabled` 保留用户的启停选择。已经启用的 A 遇到依赖问题仍显示开关已开启，并可手动停用；修复依赖不必重新选择 A 的启用状态。
- 插件列表与设置详情显示直接依赖 ID 和阻断原因。依赖缺失、停用、不兼容或循环时，Core 返回 `dependencyError: {code, message}`；插件贡献的导航、聊天入口及“发送”按钮撤下，修复后恢复。尚未启用的插件不能在依赖未满足时启用。
- 依赖进程启动失败或退出时，进程诊断可显示 `dependency-blocked`（“依赖不可用”）及原因。Core 暂停受影响的运行中依赖者；依赖恢复后在下次业务请求或事件到达时重新按顺序启动，不自动重跑已中断任务。
- 依赖未满足时仍可预先编辑并保存插件默认设置，相关业务管理入口暂停开放；设置草稿和插件资料保留。

`self-context` 等由 Core 转接、允许 `available: false` 后继续运行的业务协作仍可作为软依赖使用。只有清单中明确声明的 `dependencies` 才会阻止依赖者启动。

## 3. 控制通道（插件契约 v1）

监督器通过插件进程的标准输入输出交换 UTF-8 JSON 行，每行不超过 4 MiB。标准输出只用于协议消息；日志使用 `plugin.log()` 的 `log` 消息或标准错误。Core 内存中最多保留最近 200 条日志、每条 500 字符；插件作者仍须避免将聊天正文或凭据写入日志。Core → 插件发送队列上限为 32 条、合计 8 MiB，管道背压不阻塞资料维护线程。

| 方向 | 消息 | 说明 |
| --- | --- | --- |
| Core → 插件 | `hello` | 协议版本、插件身份与资料目录、Core 接口地址和本进程令牌；模型服务通过 `GET model/services` 另取 |
| 插件 → Core | `ready` | 声明支持的协议版本；10 秒内未就绪视为启动失败 |
| 插件 → Core | `heartbeat` | 每 5 秒一次；连续 3 次缺失标为“无响应” |
| Core → 插件 | `rpc` | 界面或宿主调用插件方法：`id`、`method`、`params`、`context`（账号、好友） |
| 插件 → Core | `rpc.result` | 对应 `id` 的 `result` 或 `error: {code, message}` |
| Core → 插件 | `task.start` | 新的任务执行：任务描述及执行编号、代次、执行令牌 |
| Core → 插件 | `task.cancel` | 协作取消；执行令牌此时已作废 |
| 插件 → Core | `task.ended` | 执行处理函数已退出；Core 核对执行及插件进程归属后处理停止确认 |
| Core → 插件 | `event` | 订阅事件，见第 6 节；插件以 `event.ack` 确认 |
| Core → 插件 | `shutdown` | 有限等待后退出；超时由监督器结束进程组 |

RPC 默认 30 秒超时，超时返回 `plugin-timeout`；进程退出等不可用情况返回 `plugin-unavailable` 等具体错误码。插件返回的业务错误保留错误码和经过长度限制的消息，界面显示原因。心跳只表明进程仍响应，不证明业务任务已经推进。

## 4. Core 插件资料接口 v1

插件通过本机回环 HTTP 访问 `/plugin-api/v1/…`，请求头 `Authorization: Bearer <进程令牌>`。与任务相关的写入另带 `X-KYF-Execution: <执行令牌>`；Core 在每次写入时复核执行是否仍为该任务的当前代次，旧执行或已停止任务的写入返回 `409 execution-revoked`。

账号与好友范围校验用于防止串写资料（正确性），不承诺阻止恶意插件。聊天读取提供分页、批量数量限制和流式导出；插件拿不到 Core 数据库连接、任意 SQL 或跨请求事务。

| 接口 | 用途 |
| --- | --- |
| `GET scope` | 当前微信账号与就绪状态 |
| `GET settings` | 当前进程所属插件的设置快照：声明、定义指纹、已保存值及版本；不需要账号或任务执行令牌，不接受查询参数 |
| `GET friends`、`GET friends/{user}` | 已添加会话中的好友及基础资料 |
| `GET history/status` | 聊天资料覆盖：状态、已读条数、来源指纹、纪元、水位线（最后一条的序号和编号），以及这份资料读取到的来源位置 `highwater` |
| `POST history/status-many` | 一次最多 500 个聊天的普通 `history/status`，共用一次来源身份核对；不含 `sourceRevision`，也不做前缀审计 |
| `POST history/prepare` | 请求 Core 读取或增量更新该好友的聊天资料；立即返回状态 |
| `GET history/messages` | 按序号分页读取（每页最多 500 条），每条带编号、序号、发送方、时间、类型、正文及内容哈希 |
| `POST history/rows`、`GET history/recent` | 按编号批取最多 500 条；读取近期消息最多 2,000 条。`recent?full=1` 返回投影行结构 |
| `GET history/export` | 截至水位线的完整快照，NDJSON 流式返回，供需要全历史的分析一次读取 |
| `GET history/context`、`POST history/verify` | 原文证据：目标消息及前后上下文；按编号与内容哈希核对是否仍然一致 |
| `GET media` | 按消息读取图片、贴纸首帧或视频帧，供视觉模型使用；`frames=2..4` 对动态表情按播放时间返回多帧 |
| `POST history/stickers` | 按编号批取最多 1,000 条表情消息的内容 MD5、商店包 ID、配字与包名 |
| `GET human/{user}` | 人工资料：已确认记忆、待确认候选（含提出插件）、联系目标、自身资料、我的观察及版本；支持 `view=snapshot` / `view=rows` |
| `POST human/candidates` | 提交记忆候选；需执行令牌。Core 过滤已忽略或重复内容，保存为带来源插件的待确认候选 |
| `POST tasks`、`POST tasks/{id}/progress`、`POST tasks/{id}/finish` | 插件发起的后台任务、进度与终态 |
| `POST tasks/{id}/stop` | 插件只能停止自己拥有的任务，供页面主动停止与业务取消使用 |
| `POST files/{token}/claim` | 领取宿主文件选择器签发的一次性授权；页面只得到授权和显示名，路径由插件后台领取 |
| `GET model/services` | 网关上可用的模型服务：协议、本机地址、模型及上下文容量；不含凭据 |
| `POST model/attempts/{id}/outcome` | 业务对某次模型尝试结果的处理与采用情况，用于诊断详情 |
| `POST subscriptions`、`DELETE subscriptions` | 动态订阅某个好友的事件，例如新消息 |

插件私有资料保存在 Core 分配的目录 `.local/plugin-data/<插件>/`：表结构与升级由插件管理，Core 只负责目录、清除账号时的删除与备份。插件写自己的数据库不占用 Core 的数据库锁。

## 5. 任务与执行

Core 统一登记插件任务，保存在 `.local/core/core.sqlite3`：

- 任务：插件与版本、类型、账号、好友、方案、标题、状态、进度、错误与时间。
- 执行：任务的一次运行；代次递增，执行令牌只保存摘要。重试或继续会创建新执行。

| 状态 | 含义 |
| --- | --- |
| `queued` | 排队，等待前一个任务结束或插件就绪 |
| `running` | 运行中；进度中可再细分“等待模型” |
| `stopping` | 已请求停止，等待插件确认 |
| `done`、`partial`、`failed` | 完成、部分完成、失败 |
| `stopped` | 用户停止 |
| `interrupted` | 应用重启或插件进程结束导致中断，显示“已中断，可继续” |

停止顺序（与需求第 2 节停止原则一致）：

1. 作废执行令牌：Core 拒绝该执行之后的写入，网关拒绝其新的模型请求并中止在途请求。
2. 向插件发送 `task.cancel`。
3. 10 秒内插件未确认结束，监督器结束该插件进程组；同一插件的其他在途任务记为中断，其他插件与资料维护不受影响。
4. 已提交的结果和检查点保留；迟到结果被拒绝，不写入新任务。
5. 应用重启后，未结束的任务统一记为中断；不自动重跑，由用户继续。

分析方案规则：同一好友同一时间最多一个方案任务在运行。切换方案只改变查看对象；在新方案上开始分析而原方案仍在运行时，界面询问“停止原方案”或“排在它后面”。排队任务在前一个任务结束后由 Core 启动；应用重启后排队任务不自动启动。

执行还绑定具体插件进程：启动消息只交给已绑定的进程，旧进程退出与旧执行结束信号不能关闭新执行。清除账号先冻结该账号的新任务、撤销执行令牌并终结全部排队项，再停止插件及删除资料，避免退出回调重新启动待删除任务。

任务查看状态（2026-10-18）：主界面好友列表和工具栏不再显示插件回答红点；聊天头像的未读标记仅反映聊天消息，点击好友会话后在本应用标为已读。插件任务的查看确认协议仍保留兼容：创建 `interactive` 任务时带 `notify: true`，以 `done` 或 `failed` 结束后可记录查看状态；用户停止的任务不计入。已读状态按任务 ID 保存在 `task_attention_seen`，重启后保留，清除账号时一并删除。主界面通过 `GET /api/attention?account=` 每 3 秒读取，只查询 Core 记录，不调用插件。读取结果包含 `taskIds` 与 `tasks: [{id, runId, threadId}]`；宿主通过 `attention-check` 事件发给可见面板，面板只为当前已加载讨论中实际显示的回答调用 `attention.seen`。宿主校验可信插件、账号与好友后，向 `POST /api/attention/seen` 提交 `{plugin, account, user, taskIds}`。只有确认成功才移除这些 ID，失败下次重试，确认期间新完成的任务保留。后台窗口不确认已读；这些内部记录不会触发聊天未读标记。

## 6. 事件

| 事件 | 来源 | 投递 |
| --- | --- | --- |
| `message.new` | Core 会话监视：只轮询有订阅的会话，合并去抖 | 带账号、好友、新消息编号和读取位置；插件确认后 Core 推进位置 |
| `friend.opened` | 用户打开某位好友的分析窗口 | 发送给该好友当前方案所属插件，用于自动增量分析 |

新消息订阅按 3 秒轮询、读取最多 40 条近期消息，每次投递最多 20 条新消息；60 秒未确认可重投，确认后推进位置。首次订阅默认从当前会话末尾开始。需要补接宿主启动后、插件订阅前消息的插件，可通过 `POST subscriptions` 的 `replayLive: true`（Python SDK：`core.subscribe(..., replay_live=True)`）明确选择宿主维护的当前运行起点；已有确认位置不会回退，不能借此重放离线历史。分析与建议使用此选项，并按好友开关的开启时间筛选，避免开启或恢复监听时漏掉刚到达的消息。`friend.opened` 和新消息投递可按需启动插件；`human.changed` 当前只通知已经运行且订阅了该事件的插件。导入的历史资料不产生 `message.new`。

## 7. 模型网关

网关是 Core 启动和监督的独立 Node 进程，为每个已配置的模型服务提供本机接口，沿用服务原有协议（Anthropic Messages、OpenAI Responses、Chat Completions、Gemini、Ollama，以及本地判断的 `systemone`）。服务包含生效用途 `roles`，主模型始终排第一；同一模型承担多个用途时只下发一条服务。插件通过 `models.service_for(role)` 选择用途，也可让 `generate(role="image")` 路由图片步骤。插件或其使用的 SDK、Agent 引擎只需把地址指向网关，并把执行令牌当作 API Key：

```text
http://127.0.0.1:<网关端口>/s/<服务编号>[~<步骤>]/<协议原有路径>
```

`models.judge(task, state, questions)` 与普通生成共用 SDK 的 Node 工作进程和任务令牌：`systemone` 直通 `/v1/systemone`，其他协议在工作进程中以 JSON 生成并校验为统一结果。两类判断分别标记 `engine`，概率阈值不能混用。本地 Julia 只允许担任判断用途，启动参数与随机密钥留在 Core／网关私有管道；自测与业务调用共用并发 1 的队列，空闲后退出。用户侧权重仅从固定 ModelScope 来源下载，运行时随安装包提供。

本地判断进程实际崩溃时是重试规则的特例：在尚未转发响应正文时仅重启并重试一次，新启动产生独立诊断记录并登记新的随机密钥供脱敏；HTTP 错误、无效答案和已取消的调用不自动重试。进程启动失败也保留失败调用记录，用量未知，不补计 token。

- 令牌可放在 `Authorization: Bearer`、`x-api-key`、`x-goog-api-key` 或 `api-key` 请求头。令牌绑定插件、插件版本、任务、执行（代次）、账号与好友范围，网关据此记录调用归属，不依赖插件自报。
- 网关转发前移除令牌并注入真实凭据；凭据只经 Core 与网关之间的私有管道传递，不写入插件配置、环境变量或日志。
- 请求中的模型必须与用户配置一致，未配置的服务或模型返回 403。
- 排队：每个模型有自己的并发额度（默认 4，可设 1–8，随服务下发的 `concurrency` 字段），所有插件共用同一服务的额度，不再有插件专属并发覆盖。降低额度不会中断已经运行的请求，新请求等待空位。等待不限数量、不限时长（2026-10-25 起）：请求只会在轮到执行或任务停止时离开队列，不会因排队人数或等待时间被拒绝；模型超时从网关真正转发时开始计算，插件 SDK 的模型进程和 Python 客户端不再自己计时，排队时间不计入超时。插件轮流获得执行机会，交互任务优先，后台任务等待 30 秒后提升到同等优先级。一个服务无响应不占用其他服务的队列；空闲槽仍可供其他插件使用。
- 排队取消、超时和获槽均清理定时器与取消监听；空队列和已释放的插件计数及时删除。获槽后再次核验执行令牌。未实际转发的拒绝、取消和过期请求不生成用量尝试。
- 取消：执行令牌作废后，新请求被拒绝，在途请求被中止；已发生的用量仍记在原尝试上。
- 网关不在协议之间转换格式，也不自动切换模型。请求正文上限 32 MiB。模型设置的 `timeoutMs` 默认 3,600,000，允许 60,000–10,800,000 的整数；界面以 1–180 分钟编辑。Core 的 `models.services` 只传此非敏感配置，真实密钥仍由网关注入。每次请求冻结等待时限，纯超时变更不改变模型内容身份，也不取消在途请求。SDK 和助手引擎使用同一时限，旧插件请求内较短的固定超时不再覆盖用户配置；取消、连接探针和其他控制操作保持独立的短时限。SDK 或 Agent 引擎重试会再次经过网关，每次实际请求单独计量；网关本身不额外循环重试。

连接测试与模型列表由同一 Node 网关进程通过私有控制管道的 `probe` → `scripts/model-probe.ts` 执行，使用既有连接器和应用级诊断。该控制路径目前不经过普通插件请求的用量账本，不归属任何好友。

Core 到网关的控制消息由每代进程独立的写线程发送，上限 256 条、8 MiB；管道写入停滞 3 秒或队列溢出时，明确终结该代网关并唤醒等待者，不能悄悄丢弃令牌撤销消息。旧代的 ready、probe 响应和退出回调不影响新代；已产生的迟到用量仍按原尝试和范围入账。Windows 停止进程组时保留成员进程句柄并等待退出，以释放子进程持有的文件及目录。

主动助手的 opencode 前面另有插件侧 `plugin-sdk/node/execution-relay.ts`。opencode 配置只包含回环中继地址和随机中继密钥；后台工作进程在一次调用期间，将原生会话绑定到本次执行令牌及步骤，中继转发时再置换为执行令牌。调用结束即解绑，未绑定会话返回 401；下一次任务可复用同一原生会话并换用新令牌。真实模型凭据始终由 Core 网关注入。

## 8. 用量账本与诊断记录

- **基础用量（常开）**：网关每次实际尝试都写入 `.local/core/usage.sqlite3`：时间、插件与版本、任务、执行、账号、好友（或“未关联好友”“多好友任务”）、服务、协议、实际模型、状态、HTTP 状态、耗时、首字时间，以及服务报告的输入、输出、推理、缓存 token。服务未返回用量时记为未知，不补零。写入走有界异步队列，拥塞时丢弃并记录缺口，不阻塞模型传输或资料维护。
- **进行中的尝试**：网关在请求进入排队、开始转发和结束时上报，Core 只在内存中保留尚未写入账本的尝试。它们排在调用记录第一页最前，状态为“排队中”或“进行中”，不计入任何汇总；最终行提交后由账本行接替，同一尝试不会出现两次。网关进程退出时，该代未完成的尝试随之移除。
- **完整诊断（开发者模式）**：开启时，网关按原有诊断机制采集脱敏后的完整请求与响应，归属到同一任务与执行。关闭开发者模式不影响基础用量。
- 清理诊断正文不清空用量；用量统计默认长期保留，可在模型调用窗口中按需清空。

账本由 `bridge/usage_ledger.py` 的独立写入线程处理，队列上限 10,000 条、每批最多 200 条。原始输入、输出、推理及缓存字段保留服务原有含义；另保存口径版本、总输入（含缓存）、总输出（含推理）、总 token 与总量来源。总量优先采用服务明确报告的计数，缺失时只按已知协议规则推导：

| 协议 | 总输入 | 总输出 | 总量 |
| --- | --- | --- | --- |
| OpenAI Chat Completions / Responses | 服务输入，已含缓存 | 服务输出，已含推理 | 优先服务 total；否则完整输入加输出 |
| Anthropic | input 加缓存读与缓存写 | output | 完整总输入加总输出 |
| Gemini | prompt 加 tool-use prompt | candidates 加 thoughts | 优先服务 total；否则完整分项相加 |
| Ollama | prompt_eval_count | eval_count | 完整输入加输出 |
| systemone | usage.input_tokens | 0 | 明确报告的输入加输出 |

缺失或 `null` 计数保持未知，不能补零；缓存及推理若已属于输入／输出子项，不再重复累加。服务报告的总量可能包含尚未完整报告的分项，不强制等于页面可见分项之和。新口径没有识别的协议仅保留其明确报告的总量，不按 OpenAI 规则推算。旧账本增量迁移只利用现存字段能确定的计数，原始字段与诊断不改写，不能从已删除的正文猜测或补造历史用量。

SQL 聚合全部匹配记录，只累加各字段的已知部分，并分别返回输入、输出、总量及缓存／推理的已知调用次数。空范围为零；范围内有调用而该字段完全未知时，界面显示“未知”。部分缺失时显示已知用量、完整度及缺失次数。`missingUsage` 继续表示原始输入／输出缺失，新增 `missingTotalUsage` 等表示规范化字段的覆盖情况。失败、取消和重试各次实际尝试已报告的消耗均计入。拥塞缺口为全账本计数，不能解释成当前账号、好友或当前筛选独有的缺口。

清空用量前由写入线程确认先前批次已处理；等待超时返回 `usage-busy`，避免显示清空成功后旧批次重新出现。关闭时停止接收记录，由写入线程处理已接受的记录并关闭数据库。尝试自身保存好友范围，因此取消后收到的多好友用量不会落入“未关联好友”。

模型调用窗口从左侧导航“设置”上方的按钮打开（复用独立窗口），默认显示所有好友：

- 默认“用量统计”，另有“调用记录”页签（原“诊断记录”已并入调用记录）。筛选包含时间、好友（全部／指定／未关联／多好友任务）、模块、模型、状态（含“进行中”），以及展开步骤后的步骤筛选。
- 汇总：已知总 token、总输入、总输出、实际请求数、失败次数与用量完整度。口径、缓存与推理计数、首条可查询记录日期按需展开；首条日期不保证此前无调用或此后持续完整。
- 时间趋势：小时／天／周／月／年，单日可按分钟查看。与关系趋势共用 `plugin-sdk/web/time-trend.js` 的日历、横滚、滚轮锚点缩放、点击、框选及边缘滚动、Shift 扩选、方向键与 Home／End。图表按模块堆叠，可切换总量／输入／输出／调用次数；不完整周期显示虚线，并仅绘制已知用量。
- 所选时间联动顶部统计、模块排行、好友汇总和调用记录；切换页签保留筛选。模块按已知总量排序，显示占比、调用次数、已知调用的单次平均，可展开各步骤并点击筛选。未识别步骤保留原始标签，缺步骤归为未分类。
- 按好友汇总：请求数、规范化总量与分项、失败次数、最近调用，可排序并点进明细。
- 调用记录：逐次尝试显示规范化总量、分项及总量来源；进行中的尝试每 2 秒刷新第一页并实时显示已用时间，结束后刷新汇总。展开后分“概览／请求／响应／过程与错误”：概览与过程来自账本，请求、响应（模型正文、原始返回、应用结果）和错误详情来自开发者模式采集，未采集时说明原因。概览可跳到同一任务的全部步骤与重试。汇总由后端聚合全部匹配记录，不是当前页相加。
- 连接测试等应用级记录和未发出模型请求的任务事件不进入账本，合并后不再在窗口中单独列出；其诊断数据仍按保留期限保存。
- `/api/usage/timeline` 接收客户端本地日历边界并按半开区间聚合，补齐空桶；长跨度分批读取全部桶，不截断历史。`/api/usage/modules` 按插件与步骤聚合。查看统计与操作趋势不启动模型请求。
- 模型选项来自当前账号符合其他筛选条件的全量记录，不受当前页或已选模型限制；主聊天切换好友不改变筛选，切换账号清空旧页面状态。旧账号的迟到读取和清除确认不能改变新账号界面。

用量好友汇总只从 SQLite 与账号隔离的进程内昵称缓存读取，不为补昵称重新扫描微信联系人或会话。缓存由正常会话读取被动更新，仅保存好友 ID 和昵称；尚未缓存时先显示 ID。清理账号及退出使旧读取失效，避免迟到结果重建已清除的缓存。好友汇总独立加载，不阻塞总量、模块与时间趋势的显示；分页调用记录不会撤销同一范围内正在读取的好友汇总。

## 9. 资料划分与迁移

每个微信账号原有的 `.local/advisor-data/<账号 SHA-256>/advisor.sqlite3` 继续作为 Core 账号库，保留：

- 聊天资料投影（`context`、`context_messages`）。
- 人工资料：记忆及版本、证据、忽略记录、去重关系、联系目标、自身资料、我的观察及其编辑暂存。
- 好友当前方案选择。

插件按账号的资料位于 `.local/plugin-data/<插件>/accounts/<账号 SHA-256>/`：

| 插件 | 资料 |
| --- | --- |
| `kyf.friend-analysis` | `analysis.sqlite3`：建档任务与检查点、分析运行、扫描、互动块、人格证据、各页结果、耗时测量 |
| `kyf.message-insights` | `insights.sqlite3`：分析与建议的开关、逐条结果，以及旧自动回复建议的设置与结果 |
| `kyf.advisor` | `advisor.sqlite3`：助手讨论、消息、运行、摘要、会话状态；`engine/`：账号引擎状态 |

`bridge/core_migration.py` 在首次使用账号时，先为表迁移在原库旁保存一次 `advisor.pre-plugins.sqlite3`，再复制所属表并记录 `.migrated` 标记。旧账号目录的引擎状态 `runtime/` 不复制：其中的原生会话绑定旧工作目录，助手以全新的 `engine/` 启动，按已迁移的讨论表重建会话。引擎目录常有超过 260 字符的路径（npm 缓存），清除账号时使用 Windows 扩展长度路径删除，不依赖系统的长路径设置。全局助手模板／技能配置从 `.local/advisor/config.json`（及既有备份）复制到 `.local/plugin-data/kyf.advisor/`。复制不覆盖已经存在的新数据，原表和原目录保留。迁移失败会阻止对应插件启动业务并报告“资料迁移未完成”；Core 聊天浏览继续可用，后续使用或启动可重试。

回退旧版本只能读取迁移时保留的旧资料：新版插件之后新增的结果不会自动回写旧库，旧版之后新增的资料也不会自动合并回已完成迁移的新版库。知己分析和助手在自己的数据库中保存经 Core API 同步的聊天副本；Core 原文投影始终是资料来源，副本通过来源指纹、纪元、水位线和内容哈希校验更新。

旧版 WechatVibe 分析的结果库只读保留，供“旧版画像”折叠区读取，不再写入。

## 10. 界面扩展位置

主界面只开放少量固定位置，插件提供数据和动作标识，由主界面按统一样式渲染；插件自己的页面在独立的渲染进程中运行，不注入主聊天执行环境。页面与渲染进程经 `/api/plugins/rpc` 调用插件方法，但不能调用 `control.` 开头的方法；这类方法只由桌面主进程持有令牌的 Core 控制路由转发（2026-10-23）。

| 位置 | 内容 | 内置插件 |
| --- | --- | --- |

- 主聊天移除“意图识别”“重置会话分析”按钮及其后台请求。
- “知己分析”按钮仍在聊天标题旁，打开当前好友的分析窗口。顶部的方案选择器显示每位好友的当前方案；切换只改变查看对象，不启动分析，不删除其他方案结果。

具体宿主为 `chatui/plugin-frame.js` 的 `sandbox="allow-scripts"` iframe，通过 `plugin-sdk/web/kyf-host.js` 的消息桥接进行 RPC；页面没有同源宿主访问权，页面 CSP 的 `connect-src 'none'` 禁止页面脚本自行联网。页面脚本尚未注册 `kyfHost.on` 监听时到达的上下文和事件（例如“继续聊这句”打开面板时的引用）暂存最多 32 条，注册后按顺序送达。页面复制须紧随用户操作；宿主文件选择只把一次性授权交给页面。沙盒页面没有 `alert`／`confirm` 和浏览器存储：确认使用页面内对话框，需要记住的选择由插件后台保存。Electron 外壳启用 `IsolateSandboxedIframes:grouping/per-document`，让同源插件页面也各有独立渲染进程。默认的按站点分组不足以隔离同一个 Core 地址下的多个插件，已用真实 Electron 死循环故障注入验证逐文档分组的恢复行为。参数定义见 [Chromium 官方源码](https://chromium.googlesource.com/chromium/src.git/+/refs/heads/main/chrome/browser/about_flags.cc)。

聊天助手由 `scripts/plugin-windows.cjs` 为每个好友创建独立窗口（2026-10-22 起取代右侧面板），窗口内加载 `chatui/plugin-panel.html` 宿主；助手仓库由主界面插件导航槽加载。方案页由 `chatui/friend-scheme.js` 加载，人工记忆和任务按钮仍属于宿主。没有可用方案时销毁原页面并撤销旧状态读取；最后一个页面的迟到消息不能继续调用插件。

### 10.1 插件设置（2026-10-14）

“设置 → 插件”的每张卡片只提供“设置”按钮和启停开关，点击“设置”进入同一设置窗口的二级页。启用状态由开关本身表达，不额外显示“已启用 / 已停用”等状态文字，也不随插件进程或窗口状态变化。正常卡片不单列“运行中 / 未运行 / 需要时自动启动”；后台进程存活不代表正在分析，窗口是否打开也不作为插件启用状态的依据。无响应、异常退出、连续崩溃阻止启动或不兼容时，才在正文显示必要的原因与诊断。需要恢复插件时，先关闭再重新开启：关闭会停止任务和进程，保留资料与设置；重新开启会清除故障阻止状态，插件在后续使用或事件触发时按需启动。返回列表、切换分类、关闭和 Escape 均检查未保存更改，提供“保存并离开 / 放弃更改 / 继续编辑”。列表的状态轮询不重建设置表单；返回恢复列表位置和原插件按钮焦点。

插件通过 `contributes.settings` 声明 `schema: 1`、`groups`（分组与字段）和可选 `description`、`links`。字段包含 `key`、`title`、`type`、`default`，可选说明；支持 `boolean`、字符串值的 `select`（`options: [{value,label}]`）、有上下限的 `integer` 和有长度上限的 `string`。最多 8 个分组、64 个字段；字段标识唯一。`links` 只允许引用本插件已经声明的 `nav` 页面。无设置声明的插件仍可打开详情，并显示暂无可调整项。

模型调度和外部搜索源属于 Core，在“设置 → 模型设置”中统一配置，插件不再声明 `maxConcurrentTasks`、`modelConcurrencyKey` 或 SearXNG 字段。插件通过 `GET /plugin-api/v1/models/settings`（Python：`plugin.core.get("models/settings")`）读取只读的 `{revision,values}` 快照；`values` 包含 `searchSource`（`none` / `searxng`）、`searxngUrl` 和 `searchOpenPages`。并发额度改为每个模型自带（服务下发的 `concurrency`，默认 4，范围 1–8），插件经 `models.service_for(role)` 取对应用途的服务。聊天助手在每轮开始时冻结搜索配置，排队中的问题在实际开始时读取；讨论压缩和资料摘要仍不联网。分析与建议按主模型并发限制本地工作线程，以保留新消息优先顺序；跨插件实际模型调用额度最终由网关统一执行。插件内残留的旧值不再覆盖核心配置。

核心将调度与联网设置独立保存在 `.local/core/model/settings.json`，不依赖模型连接或插件启用状态。首次读取时迁入聊天助手的旧搜索配置；旧的全局并发总额在读取时忽略，改由主模型条目自己的 `concurrency` 承接（迁移模型存储时折算）。旧文件保留。主窗口通过 `GET/POST /api/model-settings` 读取或保存完整 `{revision,values}`；版本冲突返回 409，插件接口只允许读取。

宿主接口由 `bridge/core_plugin_settings.py`、`core_plugins.py`、`core_http.py` 提供：

- `GET /api/plugins/settings?id=<插件ID>` 返回 `{plugin,schema,definition,values,revision,enabled,effective:"next-task"}`；`definition` 是规范设置声明（包含链接）的 SHA-256，无声明时为 `null`。
- `POST /api/plugins/settings` 接收 `{id,revision,definition,values}` 并返回同形快照。`values` 为完整表单，省略字段恢复声明默认值，未知字段被拒绝。配置版本冲突返回 `409 settings-conflict`，声明已变化返回 `409 settings-schema-changed`，字段错误返回 `422` 和 `detail.fields`。前端保留草稿，由用户选择是否重新读取。
- 配置保存在 `.local/plugin-data/<插件ID>/settings.json`，文件结构为 `{schema:1,revision,values}`。Core 串行校验和原子写入，文件上限 64 KiB；损坏文件和写入失败时保留原文件。插件升级后读取时忽略已经移除的旧字段、新字段使用默认值，不自动改写文件；用户明确保存时才写入新声明对应的完整表单。已声明字段类型不兼容仍明确报错。宿主读写设置无需启动或启用插件，停用后仍可预先配置。
- Python 插件通过 `plugin.core.settings()` 或 `get("settings")` 读取自身设置；`kyf_plugin.settings.read_settings` 校验业务需要的字段并返回独立快照。提示词等任务行为配置在任务接受时读取一次；调度容量读取核心模型设置。保存不取消或重启已经运行的任务，也不重新生成已有结果。

插件业务设置：知己分析的“自动增量更新”；分析与建议的“默认回复语气”（自然 / 简短 / 礼貌）；聊天助手的“使用关系记忆 / 使用用户观察”，并链接到已有助手仓库管理模板与技能。外部聊天识别使用统一模型设置，没有独立的模型并行数量表单。关闭助手资料引用只影响后续问题直接加入的资料，已有讨论中提及的内容保留。按好友开启分析与建议仍在聊天页操作，不因插件启用或保存默认设置而为所有好友开启。外部搜索源默认不配置即不联网，可选本机或自建的 SearXNG，配置入口及使用边界见 `docs/advisor.md`。

三个插件继续使用应用默认模型，连接及密钥集中在“设置 → 模型设置”，不进入插件配置。宿主表单位于 `chatui/plugin-configuration.js`，样式与卡片共享 `plugin-settings.css`；新增宿主脚本和后端配置模块均加入 `scripts/stage-real-client.py` 的资源输入。

## 12. 插件开发

- Python 插件可使用 `plugin-sdk/python/kyf_plugin`：控制通道循环、Core 接口客户端、任务上下文（取消、进度）、插件资料库帮助函数。

- 插件只依赖本文接口和自己的代码，不导入 `bridge/` 中的 Core 模块，也不读取其他插件的资料目录。

Python SDK 的 `ModelClient` 会启动插件所属的 Node 工作进程；该工作进程复用 `electron/model-connectors.ts` 的通用协议适配器并将地址固定为 Core 提供的服务地址。代码目录沿用历史结构，不能仅凭文件位于 `electron/` 就认定它承担 Core 分析业务。提示词、资料取舍、摘要策略、业务重试和输出解析分别留在插件中；Core 负责资料和转发，不替插件生成摘要。

助手 Node 引擎位于 `plugins/kyf.advisor/engine/`，界面组件源文件在 `ui-src/`，`npm run build:advisor-ui` 输出 `ui/advisor-ui-bundle.js`。`scripts/stage-real-client.py` 携带 `plugins/` 与 `plugin-sdk/` 文件树，排除 `tests/`、`node_modules/`、`__pycache__/` 和 `.pyc`；运行资料保存在包目录外的 `.local/`。旧助手 Core 路径不再作为打包输入，许可与第三方声明随代码保留。
