# 开发者模式与模型调用记录需求

产品：知己微信助手 · Zhiji WeChat Assistant。需求版本：v0.4（2026-10-13）。状态更新：2026-11-02，已在本地 `dev` 实现全局入口、基础用量账本及独立窗口。当前实现和验收状态见[开发者模式实现与验收](developer-mode.md)，品牌名称按[当前约定](branding.md)更新。

当前状态：左侧常驻入口、当前账号全好友筛选、token 汇总、进行中调用、请求／响应／错误详情均已有实现；基础用量常记，完整正文由开发者模式按需采集。调用与诊断记录已合并为“用量统计／调用记录”两个页签。下文保留原需求和历史验收标准，真实客户端与发行环境的共同验收见[需求待办清单](requirements-todo.md#validation)。

## 2026-10-13：全局模型调用与基础用量（已实现）

用户在[软件插件架构讨论](analysis-plugins-requirements.md)中确认：模型路由和监控属于 core；模型调用查看不再放在单个好友的操作层面。

| 事项 | 已确认的新要求 |
| --- | --- |
| 入口 | 左侧导航栏独立“模型调用”按钮，位于设置上方 |
| 默认范围 | 展示所有好友的调用数据，支持按好友筛选 token 用量 |
| 基础记录 | 调用归属、状态、耗时和 token 常记，不依赖开发者模式开关 |
| 完整诊断 | 完整提示词和回复仍按需采集，由开发者模式单独控制 |

建议全局入口常驻，不要求选中好友。主聊天切换好友不自动改变面板筛选；账号权限和切换时撤销旧读取仍保留，“所有好友”不自动扩大为所有账号。面板采用主内容区还是复用已有独立窗口尚待确定，入口位置不代表容器已经改变。

建议增加“按好友汇总”与“调用记录”两个视图，提供时间、好友、插件、模型和状态筛选。好友汇总展示请求数、输入／输出 token、已知总用量、失败数和最近调用；点好友进入明细。汇总在后端覆盖筛选范围全部记录，不只计算当前分页。调用详情继续复用现有请求、响应和任务链查看能力。

用量按实际模型尝试计量；网络重试和兼容回退各自记录，流式片段不重复累计。失败、取消或未采用的结果如已有服务用量，仍计入原尝试。应用缓存复用不增加模型用量；服务端缓存与 reasoning 按协议包含关系展示，避免重复相加。无好友调用和无法可靠分摊的多好友调用单独归类，全局只计一次。服务未提供用量显示未知，估算另列，不补零。

基础用量与完整诊断需有不同的存储及保留规则。建议清理提示词／回复正文不清空用量统计；基础用量保留多久、如何主动清理仍待确认。统计显示覆盖范围与缺口，既有未采集历史不补造。监控采集与聚合不得阻塞聊天维护或插件执行；发生存储故障时允许有界降级并明确缺口。

**与下文 v0.3 的衔接：** 以下第 1–12 节保留原有已实施设计和验收依据。其中“聊天右上角入口”“默认跟随当前联系人”“关闭开发者模式后停止全部调用记录”的规则已由本节取代。完整诊断开关、正文脱敏和详情等其他规则继续适用；基础用量常开不意味着完整正文默认采集。全局入口与账本已有后续实现和合成窗口验证，不能仅用早期嵌入面板的验收数字代表当前版本。

## v0.3 已实施设计与验收依据

开发者模式让用户从聊天界面检查每一次模型调用：由什么功能触发、实际发送了哪些提示词和上下文、模型返回了什么，以及失败发生在哪一步。设置中开启采集后，聊天面板右上角出现“模型调用”按钮，点击打开与“知己分析”一样独立于主页面的桌面窗口。停止采集后仍可从设置查看已有记录，查看本身不重新开启采集。

本文件定义需求与验收标准，具体已验证范围以实现文档为准。用户已明确要求设置开关、聊天右侧入口、逐条查看请求与结果；下文的交互细节、容量和保留期限为本稿建议默认值。

## 1. 目标和范围

用户应能直接回答以下问题：

| 问题 | 必须提供的信息 |
| --- | --- |
| 它是怎么调用的 | 触发功能、联系人或后台任务、调用链、实际模型与协议、时间、参数、重试和兼容回退 |
| 提示词是什么 | 这次实际发送的系统提示、用户输入、历史、资料、工具定义及工具结果；保留角色和顺序 |
| 出现了什么问题 | 失败阶段、错误码、服务响应、已收到的部分内容、重试原因和最终处理结果 |
| 模型回答了什么 | 原始返回、流式累积正文、结构化解析结果及最终被应用采用或丢弃的情况 |

首版核心包括：采集开关与独立的历史查看入口、独立记录窗口、任务关联、请求和响应详情、实时更新、基本筛选、复制、有限的本机保留与清理，以及第 7 节全部可达模型路径的覆盖。真实 provider 请求、助手完整调用链、凭据脱敏、账号隔离和删除边界均为必需能力。

独立窗口可移动和调整大小。跨重启记忆窗口位置、大小与筛选，以及固定联系人范围属于体验增强项，可在核心交付后补齐；未实现时使用本稿默认布局和跟随当前聊天的筛选。其余标为“建议”的具体数值作为本稿默认验收值，在第 12 节冻结交付范围时集中复核；调整须更新本稿及对应验收，不能由实现自行降低。采集可行性验证通过后再冻结首版方案和工期，不以缩减真实请求或助手路径覆盖代替验证。

首版不包含：编辑提示词并重新发送、自动重放请求、修改模型配置、暂停或取消业务任务、在线分享、自动上传日志、批量导出聊天正文、成本计费平台。查看、复制、刷新和筛选均不得产生新的模型请求。诊断面板不改变助手、自动回复建议或聊天分析的行为。

## 2. 当前项目基础

以下为当前工作区源码事实；不能只根据旧需求文档判断实现状态。实施时需复核后续变更。

| 路径 | 当前实现 | 对本功能的要求 |
| --- | --- | --- |
| API 消息标签与画像 | `electron/model-connectors.ts` 统一适配多种协议；业务层另有解析、校验与重试 | 在实际传输边界记录每次请求，在业务层补充解析和采用结果 |
| 主动聊天助手、自动回复建议、资料摘要与讨论压缩 | `electron/advisor-runtime.ts` 驱动独立 OpenCode 引擎；原生会话、读资料工具及压缩可能产生多次模型调用 | 必须覆盖引擎内部最终发给服务商的请求，不能只记录 `session.prompt` 的应用提交参数 |
| 媒体识别、知己分析提取与去重 | Runtime 的 `inspectMedia`、`generate` 直接使用模型连接器，不全部经过 OpenCode | 共用底层采集，但保留各自的来源、联系人和父任务 |
| 本地 Laya 分析 | 本机 ONNX 推理，不经过 HTTP 模型接口 | 用“本地推理”类型记录有业务意义的推理批次，显示输入和分数结果，不伪造远程响应 |
| 返回处理 | API 流式标签已有格式转换；部分接口只向上返回文本，原始用量或结束原因未完整传递 | 必须在转换之前采集，不能把转换后的标签称为模型原始返回 |
| 设置与界面 | 通用设置已有开关形式；聊天头部右侧已有“知己分析”“聊天记录” | 复用现有视觉样式，新增“开发者模式”与“模型调用”入口 |
| 助手右栏 | 桌面助手使用独立的 WebContentsView | 记录窗口独立显示，不隐藏助手、不改变主窗口布局 |

已有普通开发日志和启动诊断遵循不记录聊天正文的约定。本功能新增独立、主动开启的本机调用记录库；普通日志、启动诊断报告和终端输出仍不包含提示词、返回正文或密钥。

## 3. 记录的单位

采用“业务任务 → 调用步骤 → 实际尝试”三层关联，列表默认逐条显示实际尝试。

- **业务任务（诊断 task）**：一次用户提问、一次自动回复建议、一次分析批次或一次压缩操作对应的一次业务执行。用户重试已结束任务、恢复已停止任务或业务恢复后启动新执行时，创建新的诊断任务，关联原业务任务与前次执行。
- **调用步骤**：任务里的一个明确目的，例如资料摘要、生成回答、提取记忆、去重。工具执行作为关联事件记录，不把读文件本身算作模型请求。
- **实际尝试**：真正发出的一次推理请求，或一次本地推理批次。网络重试、改用非流式、移除不支持的参数后重发都创建新记录，不能覆盖前一次。

一次 HTTP 请求的流式分片归属于同一条记录，不按分片增加调用次数。连接器将非流式返回转换成内部流式事件时，也不得凭空增加一次请求。

诊断 `taskId` 对应一次执行，`businessJobId` 对应可持久恢复的业务任务，`executionId` 区分同一业务任务的各轮执行；`resumeOfTaskId`／`retryOfTaskId` 关联前次诊断任务。已有业务 job、thread 或 run ID 即使复用，也不得直接当作跨执行唯一的诊断 task ID。自动网络重试属于原诊断任务中的新尝试；只恢复诊断事件通道或补读记录，不产生新的执行或模型请求。停止前的迟到事件仍归属原执行，不写入恢复后的任务。

例如一次助手提问可能呈现为：

```text
任务：围绕当前聊天生成建议
  资料摘要         尝试 1   完成
  助手读取资料     尝试 1   完成 → 请求 read 工具
  工具事件                  已读取资料
  助手生成回答     尝试 1   HTTP 429
                   尝试 2   完成 → 已展示回答
合计：4 次模型请求，1 次工具执行
```

上例仅示意关联关系，不规定实际引擎一定采用这些步骤。应用提交给引擎的操作、引擎读资料、请求服务商必须准确区分。

未进入推理边界的排队、配置校验失败、缓存命中或业务取消，以任务事件展示，注明“未发出模型请求”，不计入调用次数。尚无实际尝试的任务也有可点开的任务事件行，调用次数显示 0，确保准备阶段失败能被找到；开始第一次尝试后关联到该任务，不重复累计。已进入传输层但网络失败的尝试保留记录，注明是否收到 HTTP 响应；没有证据时不能宣称服务商已接收。

## 4. 设置与启停

在“设置 → 通用”底部增加“开发者模式”分组：

| 控件 | 行为 |
| --- | --- |
| 开发者模式（采集开关） | 默认关闭；开启生效后采集新尝试并显示聊天入口；不控制历史是否可查看 |
| 说明 | “开启后，在本机记录模型请求、提示词、返回内容和错误，可能包含聊天正文。覆盖本机各账号、窗口及后台任务，重启后恢复设置。API 密钥不会保存到记录中。” |
| 记录保留 | 默认最近 7 天；可选 1 天、7 天、30 天；同时受容量上限约束 |
| 存储状态 | 显示当前占用、记录数、开启偏好与实际采集状态；暂停时说明原因和时间范围 |
| 查看调用记录 | 无论采集开关是否开启均可使用，按当前有效账号或应用级作用域打开已有记录；无历史时显示对应空状态 |
| 清空调用记录 | 清理本机全部调用记录，确认框明确包含所有账号；不清理聊天或模型分析结果 |

开关是本机应用级偏好，由后端持久化，覆盖主窗口、助手视图、其他业务窗口及后台任务；不能只保存在页面的 localStorage。重启后恢复已保存的开关及保留期限，多窗口保持一致，并可在设置中确认是否正在记录。开启失败保持关闭，保留期限保存失败沿用原值，不显示虚假的保存成功。关闭先停止本次运行的采集，再持久化偏好；保存失败显示“本次已停止，关闭设置未保存，重启可能恢复原设置”，可重试保存，不因写入失败恢复本次采集。

启停边界：

1. 开启只记录生效后开始的实际尝试，不补录旧历史。生效前已开始的请求标为“开启前已开始，内容未采集”，不显示成完整记录；之后的新重试可以正常记录。
2. 关闭立即停止新采集并隐藏聊天头部快捷按钮；已有业务任务继续。已打开的记录面板保持可查看，显示“采集已关闭”；重新查看可使用设置中的入口。对正在采集的尝试标记“采集已停止，记录不完整”，不能把它标为模型失败或取消。
3. 关闭不删除已保存记录，保留期清理继续适用；无需重新开启即可查看未过期内容。关闭期间不更新这些记录的正文，也不补写之后发生的业务终态；维护采集状态、删除和清理仍可进行。
4. 清空记录不取消业务任务。通过采集版本隔离，清空前正在执行的尝试不得因迟到事件重新写回；清空后开始的新尝试正常采集。
5. 开关切换由后端发布采集版本，存活且承担采集的进程确认；不等待已退出进程或只负责查看的窗口。UI 在确认前显示“正在开启／正在关闭”。确认等待上限建议 5s；开启失败或超时保持关闭，显示未就绪组件及可重试原因。关闭时先使后端旧版本接收权限失效，即使生产进程尚未确认，旧事件也不得入库；超时显示“已停止保存，部分采集进程未确认”，不能虚报全进程停采。快速切换只认可最新操作版本，旧操作的迟到确认不得覆盖新状态；不自动重启引擎或取消任务。未确认进程重连后须先获取最新状态，不能按旧版本继续投递。
6. 开关、采集版本和记录健康状态不参与模型配置指纹，不改变 provider 地址、业务请求参数、原生会话或引擎进程；中继的生命周期要求见第 8.2 节。

开启偏好与实际健康状态分开保存和展示。存储故障或拥塞只将采集置为“已暂停”，不修改用户开启偏好。暂停期间不追加正文，保留可确认的缺口；已开始采集的记录结束本轮采集并标不完整。后台按有上限的频率检查诊断存储，不调用模型；故障解除后创建新的采集版本，自动恢复之后开始的新尝试。暂停期间已开始的请求不补录，也不从恢复时刻续接成完整记录；界面保留暂停起止时间、原因和恢复状态。关闭开关后故障解除，不自动开启采集。重启时先恢复删除约束并检查存储，再依已保存偏好决定是否采集。

## 5. 聊天入口与独立窗口

### 5.1 入口

在主聊天头部右侧操作区，“聊天记录”右边增加“模型调用”按钮，仅开发者模式开启时显示。没有选中联系人时也可打开，默认查看当前账号全部调用；未选择账号时只显示应用级连接测试等记录。

设置中的“查看调用记录”始终可用，与聊天快捷入口打开同一独立窗口并遵守相同作用域。采集关闭时窗口明确显示“采集已关闭”；开启但故障暂停时显示“采集已暂停”及原因。历史查看、复制、刷新及事件补读均不改变开关。

按钮可显示当前筛选范围内、仍在采集的进行中尝试数；已停止采集且业务结果未知的记录不计入此数。业务任务的未解决错误与采集健康异常使用独立文案／提示，含义见第 6.5 节。后台任务曾经失败后重试成功，不持续作为未解决错误提示。入口不自动展开、不抢焦点。

### 5.2 窗口布局与生命周期

采用单个独立桌面窗口，默认 960×760px，最小 600×480px；屏幕可用区域不足时按可用区域缩小。支持移动、调整大小、最小化和最大化。窗口内上方为列表，下方为选中记录的详情，避免再挤出两列细长正文；保留清晰的关闭按钮。主页面不预留记录侧栏，也不压缩聊天区域。重复点击任一入口时显示并聚焦已打开的窗口，不创建重复窗口。

```text
模型调用                                   正在记录  ×
当前联系人 ▾  全部功能 ▾  全部状态 ▾
今天 ▾   搜索调用编号、模型或错误
时间      来源        状态       耗时
14:32:08  聊天助手    完成       2.4s
14:32:04  回复建议    返回异常   1.8s
14:31:59  资料摘要    接收中     6.1s
────────────────────────────────────────────────────
聊天助手 · 第 2 步 · 尝试 1
概览  请求  响应  过程与错误
实际发送内容／原始返回／解析结果
…可折叠、可搜索、可复制的正文…
```

沿用现有浅色、深色主题和紧凑列表样式。状态同时使用文字和颜色。代码字体用于 JSON，中文说明使用正文样式；默认折行，可切换横向滚动。支持键盘操作，关闭后返回主窗口。Esc 先关闭窗口内浮层，再关闭记录窗口，不干扰中文输入法组合输入。

与主页面的关系：记录窗口和聊天助手、知己分析可同时显示。打开或关闭记录窗口不改变助手可见性、会话、草稿、滚动位置或后台生成。主页面切换视图不关闭记录窗口；联系人范围默认跟随当前聊天，账号切换立即清空旧账号列表、详情和缓存并撤销旧读取。关闭记录窗口不停止采集。主窗口退出、关闭或重新载入时关闭记录窗口并撤销在途正文读取，重新打开时只使用当前有效作用域。

### 5.3 列表与筛选

- 默认当前账号、当前联系人、当天全部功能；可切换到当前账号全部调用。应用级连接测试单独提供“连接测试”范围，不混入联系人记录。
- “当天”按客户端本地时区及尝试开始时间计算；默认列表额外纳入当前作用域内仍在采集的跨日尝试，标“跨日进行中”。跨日记录在面板打开期间结束后仍留在列表，直到用户刷新或改变筛选；不因终态更新自动消失。显式选择的历史时间范围严格按起止时间筛选。切换时区后重新计算日期分组，不改变记录本身时间或保留期限。
- 提供功能、状态、时间范围和模型筛选；搜索针对调用编号、任务编号、模型名和错误码，首版不建聊天正文全文索引。
- 一行显示开始时间、功能名称、步骤／尝试序号、状态、耗时；查看全账号时补充联系人。模型、用量及简短错误可作为次行信息，避免表格过宽。
- 点击行查看详情；详情中的“同一任务”可列出该任务的所有步骤和重试。已过期或未采集的步骤明确占位，不能让剩余步骤看起来是完整链路。
- 新记录默认按开始时间倒序；查看旧记录时不跳到最新、不替换当前选择，显示“有 N 条新记录”。
- 列表支持分页或虚拟滚动，首次至多加载 50 条元数据；未点开详情不预取完整提示词和响应。
- 切换联系人时默认跟随当前聊天。体验增强阶段可提供“固定当前范围”，仅固定账号内的联系人，不固定日期；固定后持续显示明确的联系人标签。切换账号必须清空旧账号的列表、详情及请求缓存并撤销旧订阅，固定范围不能跨账号延续。
- 已打开窗口再次从入口聚焦时保留有效筛选和详情，并同步当前联系人；“当天”同步当前日期。关闭窗口后重新打开时使用当前账号、联系人和日期的默认范围，不保留旧正文缓存。切换账号后恢复该账号的默认范围；跨重启记忆非敏感筛选属于体验增强项。
- “暂无记录”“筛选无结果”“开启前未采集”“记录已过期或删除”“记录服务不可用”分别显示，不统一为一个空列表。

## 6. 单条记录详情

### 6.1 概览

显示功能、触发方式（手动／自动／后台）、关联联系人或群聊、助手会话、任务与步骤编号、尝试序号、实际模型、配置协议、实际传输协议、经过脱敏的服务地址和请求路径。协议转接存在时分别标明，不能只用设置名称代表实际网络格式。

时间包括排队、发出请求、首个响应字节、首段可见正文、结束。区分“开始收到响应”和“开始输出正文”；服务商先发心跳或推理内容时，两者不相同。未知阶段显示“未采集”，不能写成 0ms。总耗时包含范围必须明确，单次请求耗时不把业务排队计入。

请求状态与应用处理结果分别展示：例如“服务返回成功；JSON 校验失败”，或“服务返回成功；任务已过期，结果未采用”。HTTP 200 不等于业务成功。

### 6.2 请求

提供两个视图：

1. **按消息阅读**：按照实际角色和发送顺序展开 system、developer、user、assistant、tool 等内容；只有协议实际支持或发送的角色才出现。展示工具定义、工具参数、工具结果、历史摘要与本轮输入。
2. **原始请求（已脱敏）**：展示发送前最终协议请求体的文本／JSON、HTTP 方法，以及允许列表内的请求头。保留有意义的字段和值，不把界面输入框内容当作最终请求。

每次调用保存当时的提示词快照。后续更换助手模板、资料、记忆或模型配置，不改变旧记录。显示提示词模板版本、资料版本及来源类型等可得信息，用于判断当时使用了哪一版内容；来源信息无法确定时标“未知”，不能根据文本猜测。

至少显示实际发送的 model、stream、输出上限、temperature、top_p、JSON／结构化输出约束、工具选项和思考相关选项，以及本机生效的超时配置。未发送的模型参数注明“未指定，由服务端决定”，不能填入推测的默认值；超时是本机配置，未设时注明“本机未设请求时限”。兼容回退必须保留修改前后各自的实际请求。

完整性边界：

- 这里的“实际请求”是客户端发送边界观察到的内容，不包含服务商未公开的内部提示或处理。
- 通过 `previous_response_id` 等机制延续服务端上下文时，显示引用 ID，并尽可能关联本机已有记录；不把历史拼接推测成完整线上输入。未获取的远程历史明确标注。
- OpenCode 的应用提交参数另标“提交给助手引擎的内容”；只有捕获到 provider 边界的内容才标“实际发送给模型”。
- 图片、音频、视频和 base64 不写入调用正文库，以类型、大小、顺序及可用的本机资源引用占位。引用不可用时显示“原媒体不可用”；不为了预览访问远程链接。
- 请求在脱敏、媒体省略或超限截断后显示明确标识。因此这里可检查有效文本与结构，但不承诺逐字节还原网络报文。

### 6.3 响应

分别展示三种结果：

| 内容 | 含义 |
| --- | --- |
| 原始返回（已脱敏） | 服务商实际返回的 JSON 或有序流式事件，可查看未被业务解析采用的字段 |
| 模型正文 | 从原始响应提取的累积文本，流式过程中持续更新，失败时保留已收到部分 |
| 应用处理结果 | 解析后的标签、回复候选、记忆候选等，以及校验、过滤、去重、采用或丢弃的原因 |

允许复制单个消息块、完整已记录文本或已脱敏 JSON；复制动作明确指向当前选定内容，不附带隐藏字段或其他记录。模型返回的 Markdown、HTML、脚本、链接都按不可信文本显示，不能执行或自动加载外部内容。

显示 HTTP 状态、服务商请求 ID、finish_reason／结束原因、usage 原始字段与可归一化的用量。input、output、reasoning、缓存读写分别展示；缺失显示“服务未提供”或“未采集”，不能补成 0，也不能将已含于 input／output 的部分重复相加。多个步骤的合计要注明覆盖了多少次请求及多少次缺少用量；首版不估算金额。

仅当服务实际返回可展示的 reasoning 字段时，单独折叠展示并标明来源；没有返回则不推测、不补生成，也不宣称能看到模型内部思考。

### 6.4 过程与错误

按时间展示排队、上下文准备、请求发出、收到响应、正文增量、工具执行、结束、解析、校验、结果采用，以及重试／回退的起因。原始高频分片留在按需展开的响应视图，时间线可聚合，不能为每个 token 渲染一行。

错误至少区分：请求构造或配置错误、连接失败、鉴权、限流、上下文超限、超时、流式中断、响应过大、输出截断、空响应、格式解析失败、业务校验失败、工具权限或执行失败、本机记录失败。

保留脱敏后的服务错误正文、状态码和应用错误码；必要的堆栈只保留项目相对路径及行号，不记录环境变量或完整进程配置。单条记录不能用后一次成功覆盖前一次错误。

建议状态文案：进行中细分“等待响应／接收中”，终态包括“完成／失败／已取消／进程中断／结果未知”。“记录不完整”作为独立标记；采集关闭、队列丢失和内容截断不等于模型失败。用户取消导致的已有响应仍可查看，但本面板自身不提供取消业务操作。

另外保存独立的采集状态：采集中、已完成、已停止、进程中断。关闭模式时将在途记录的采集状态置为“已停止”，实际业务结果保持未知；不让这些记录永远显示运行中。保留期与容量回收按记录是否还允许追加判断，不能依赖无法再收到的业务终态。

### 6.5 列表状态、筛选与任务错误

传输状态、应用处理状态、结果采用情况和采集完整性分别保存。列表用请求状态与应用结果的组合文案，附独立的完整性标记；不能仅凭 HTTP 状态生成“完成”。本地推理使用“推理成功／失败”，不显示 HTTP 文案。

| 实际情况 | 列表展示 | 状态筛选归属 |
| --- | --- | --- |
| 正在等待或接收，采集有效 | 等待响应／接收中 | 进行中 |
| 返回完成，业务尚在解析或校验 | 返回成功 · 处理中 | 进行中 |
| 返回成功，处理成功并已采用，或业务明确无需采用 | 完成 | 完成 |
| 请求失败、流式中断，或返回成功但解析／校验失败 | 请求失败，或返回成功 · 解析／校验失败 | 错误 |
| 返回成功，任务失效等原因导致结果未采用 | 返回成功 · 结果未采用 | 未采用；不自动归为错误 |
| 用户取消业务，仍保留部分响应 | 已取消 | 已取消；可同时有记录不完整标记 |
| 停采、暂停或进程中断后，实际业务结果无法确认 | 采集已停止／进程中断 · 业务结果未知 | 结果未知；记录不完整 |

“记录不完整”是可叠加的独立筛选，不自动将业务归为错误；单项正文达到上限可保留已知业务终态。“错误”筛选包含历史失败尝试及未发出请求的任务错误事件，重试成功不移除前次失败。结果采用待定显示“处理中”；非生成型或辅助步骤不适用采用判断时明确标“不适用”。

任务尚有重试时显示“重试中”；最终失败或需要用户处理的任务错误才进入“未解决错误”提示。任务后续成功则解除其提示，保留失败尝试。存储或采集故障进入独立健康提示，不计入业务错误数。采集缺失导致无法判定任务结果时显示未知，不自行宣称已解决。

## 7. 必须覆盖的调用来源

| 来源 | 记录边界 |
| --- | --- |
| 主动聊天助手 | 每轮实际 provider 请求，包括读资料前后、工具循环中的后续请求；绑定助手会话与本次运行 |
| 自动回复建议 | 单独任务类型，绑定触发的新消息；不能混入用户主动助手对话 |
| 微信资料摘要 | 分段摘要及合并摘要逐次记录，关联触发它的助手任务；复用摘要时注明缓存命中 |
| 讨论压缩与会话恢复摘要 | 自动和手动注明触发原因；原生压缩以及恢复时新增的摘要请求都需记录 |
| API 消息情感与意图 | 按实际批次记录请求，保留批内消息关联和模型原始返回，再展示解析标签 |
| API 人物画像 | 当前分类器请求及任务层重试；记录输出截断、分片和结果校验，不能只保存最终评分 |
| 知己分析记忆提取与去重 | 每个分段、重试、拆分及去重请求，关联同一次建档或更新任务 |
| 媒体理解 | 每次视觉模型请求；显示实际文字与媒体占位，不复制媒体二进制 |
| 模型连接测试 | 测试推理单独记录为应用级来源；“获取模型列表”只算辅助网络事件，不算推理 |
| 本地 Laya | 按实际问题批次记录输入、问题及候选、输出分数或标签；WebGPU 失败后回退 CPU 保留两次尝试；不记录矩阵运算、每 token 内部状态 |

同一底层请求只创建一条实际尝试，不因 Python、Node、SDK 各观察到一次而重复计数。兼容旧入口若仍可触发推理，也须进入共用采集；已废弃且不可达的实现不单独列为新功能。后续新增模型能力必须接入相同契约。

本地 Laya 属于分类推理，详情展示问题组、实际消费的上下文、预算裁切、模型版本、设备和概率结果；HTTP 状态、远端地址和生成 token 标为“不适用”。调用次数分别列明 API 请求与本地推理，不能将分类结果中的固定 output_tokens=0 当成生成模型用量。

Laya 初始化建会话失败和合成 probe 属于应用级运行事件，不计为联系人业务推理。实际业务批次已进入 WebGPU 推理后失败、再改用 CPU 执行，才记录为同一步骤的两次尝试；设备未就绪导致业务批次尚未进入推理时，仅记录准备失败事件。问题组、预算裁切和上下文由业务层附加，实际设备执行与回退由推理边界确认。

## 8. 采集与实现边界

### 8.1 建议分层

| 层 | 职责 |
| --- | --- |
| 业务服务 | 创建任务、附加账号／联系人／会话／功能，记录上下文准备与应用处理结果 |
| 实际推理边界 | 捕获最终请求、每次尝试、原始响应或流式事件、传输错误及时间 |
| 统一采集服务 | 校验采集来源、作用域和版本，先脱敏再进入诊断 IPC、缓存与存储，限量缓冲、幂等去重、记录完整性 |
| 独立本机存储 | 保存元数据、正文与事件，提供分页、详情、删除和保留期清理 |
| 只读查看界面 | 查询与展示，不接收模型凭据，不参与提示词生成及业务结果回写 |

建议新增独立的 trace 契约、采集模块、存储模块、HTTP 接口和前端面板；本稿不冻结文件名。不要把整个功能继续堆入 `app.js`、`backend_service.py` 或模型连接器。

连接器在最终 fetch 边界和 SDK 转换前采集，业务层另补解析结果。要兼容 Request 对象和参数式调用，避免遗漏最终 body。读取流不能消费掉业务响应、改变分片顺序或使业务等待磁盘；不能依靠无界复制流缓存。

实际模型传输与解析进程可短暂持有原始请求／响应，受限脱敏工作缓冲也可为识别分片边界暂存原始内容；处理后及时释放。此例外不允许未脱敏内容进入诊断跨进程事件、查询缓存、普通日志、UI 或持久层，也不改变发给模型的实际内容。第 9 节缓冲预算包括新增的诊断工作缓冲。

Python → Node → 引擎 → provider 传递明确的关联标识。工具后续步骤、原生自动压缩和并行助手任务必须保持归属；禁止靠“当前选中的联系人”、全局最近请求或并发请求顺序推断归属。关联标识保留在本机，不额外向模型服务商发送联系人或账号信息。

### 8.2 OpenCode 采集是首要验证项

当前 Runtime 控制接口观察不到引擎最终组装的全部模型输入。实施第一阶段必须使用固定版本引擎和合成会话，验证：系统提示、历史、工具定义、读资料结果、自动压缩、重试能否在 provider 请求边界捕获并正确关联。

当前项目固定引擎为 OpenCode 1.18.34；实施时核对锁定版本、SDK 与运行包的一致性。验证产出“业务来源 × 配置协议／实际传输协议 × 流式／非流式”的可达与支持矩阵、合成服务收包对照、并发归属证据和启停连续性结果。矩阵覆盖当前可配置的 Responses、Chat Completions、Anthropic、Gemini 和 Ollama 协议；业务路径不支持的组合标“不适用”并给依据，不能把未验证组合当作通过。Ollama 配置在直接连接器走原生接口、在当前助手引擎走 OpenAI-compatible /v1 时，按两种实际传输分别验证，不能共用一个通过结论。

优先使用引擎可支持的 provider／传输扩展点；确无可用扩展时，评估仅服务于本应用的本机中继。具体方案以验证结果选定，不承诺现有 SDK 已提供所需能力。若采用中继，必须保留原协议、流式、取消、超时及现有服务地址校验，只监听回环地址、使用进程级认证、不扩大到通用代理，不将令牌写入访问日志，也不引入外部追踪服务。

采集开关和版本不得进入 provider 配置指纹，也不得在启停时修改其 baseURL。若采用中继，路由与生命周期独立于采集开关安排，开关只切换诊断采集；正在运行的请求保持原路由、引擎 PID、会话及流式连接连续。中继断开后不得由诊断层自动重发业务请求，失败沿用原业务错误与重试处理。该约束需以流式生成中启停、故障和重连实测，不只检查静态配置。

仅能拿到 `session.prompt` 参数或最终回答时，不满足本功能的助手路径验收。界面应准确标“引擎请求内容未完整采集”，该缺口须解决后才能声称首版覆盖全部调用。

首要验证未通过时，记录失败路径、协议、原因及备选方案，继续解决采集边界；在此之前不冻结完整实现工期或将该路径标为完成。可继续建设已验证的共用基础，但不得用应用提交参数替代实际请求来通过核心验收。引擎或 provider 适配依赖升级后，重新验证受影响矩阵及核心助手调用链。

### 8.3 核心记录契约

| 字段组 | 最低要求 |
| --- | --- |
| 身份与关联 | schema 版本、record ID、task ID、businessJobId（可得时）、executionId、resumeOfTaskId／retryOfTaskId、step ID、父步骤／重试来源、attempt 序号、采集版本 |
| 作用域 | 后端确认的账号、联系人或群聊、助手会话／运行 ID、删除版本；应用级任务使用独立作用域，查看会话另绑定账号切换版本 |
| 来源 | 功能类型、触发方式、模板与资料版本、触发消息或批次引用 |
| 调用 | 类型、配置协议与实际传输协议、实际模型、脱敏地址、参数快照、流式标记、本机运行与引擎版本 |
| 内容 | 脱敏后的请求、响应事件／正文、应用处理结果、媒体占位、eventSeq、contentId、chunkIndex／字节偏移、可得的总长度或结束标记 |
| 状态 | 传输状态、业务处理状态、采集状态、结果采用情况、错误、重试／回退原因 |
| 计量 | 各阶段时间、可得用量原值及归一化值、计量来源；缺失为 null |
| 完整性 | 请求／响应各自是否完整、截断／脱敏／省略／丢失原因、已保存字节数、可得的原始字节数 |

完整诊断事件的去重键使用实际尝试 ID 与事件顺序号 `eventSeq`；分块信封另以实际尝试 ID、eventSeq、事件内内容标识 `contentId` 和块编号 `chunkIndex` 去重，不能把同一事件的后续块当重复投递丢弃。同键同内容为重复投递，同键不同内容报告诊断协议异常并标缺口，不能覆盖原块。协议事件顺序与传输块顺序分开保存；乱序信封可在预算内重排，等待超时或预算不足时标不完整并结束对应采集，不等待业务。跨进程重连、重复投递不得重复生成记录或正文。崩溃重启后，对于无法确定结果的进行中记录标“进程中断，结果未知”，不伪造超时；恢复记录不得自动重发请求。

诊断传输按脱敏后的 UTF-8 字节数分块，单个传输信封（含元数据）上限建议 64KiB；分块保留原始事件顺序、内容偏移及结束信息，按块保存并分页展示已保存文本，不要求界面先加载全量才能查看。仅在内容完整时按完整协议事件解析；缺块或截断后仍可查看、复制已保存片段，但显示不完整标记，不能称为完整 JSON。重组工作缓冲也受全局预算约束，不把传输块计为模型分片或新尝试。超大工具定义、消息块或响应事件同样分块，不能依赖现有通道能传输整份 16MiB 正文。业务控制事件与诊断大正文使用独立队列或明确的优先级与预算；慢消费者、断线或写入拥塞只允许诊断内容停止采集并报告缺口，不使业务控制或响应等待。

建议接口语义：读取／更新设置、分页查询元数据、按作用域读取详情与正文、接收增量事件、清空记录。增量通道可沿用适合项目的事件机制；断线后按游标补读，记录已清理则明确返回失效并重新查询。仅打开面板才建立详情订阅；关闭面板不停止后台采集。

### 8.4 可信身份与接口权限

本机回环绑定和 HTTP Host／Origin 校验是必要边界，不能单独代替诊断接口的身份校验。认证机制在采集边界验证阶段选定，凭据不进入记录、URL 或访问日志；IPC 须校验发送窗口、主框架和允许的消息类型。接入现有本机服务时核实真实认证能力，不能假定普通接口已有进程令牌保护。

| 权限类别 | 允许主体与校验 |
| --- | --- |
| 读取元数据、详情、正文、订阅及补读 | 受信客户端会话；绑定后端确认的当前账号与切换版本，逐次核对记录归属 |
| 写入增量及采集健康事件 | 已登记的采集进程／实例；校验其执行、作用域、采集版本与删除版本，普通查看页面不得伪造写入 |
| 开关、保留期限、清空及作用域删除 | 具有相应控制权限的受信客户端；全账号清空是明确的应用级操作，不提供跨账号合并正文读取 |

查询参数中的 account、record ID 或补读游标只是待校验目标，不是身份凭证。账号切换后旧读取会话版本和订阅失效；发送前及异步返回时均复核版本，旧账号数据不得进入新账号视图。应用级连接测试以独立范围授权，不因选择了账号而混入联系人记录。采集进程绑定任务创建时的业务作用域；查看窗口切换账号不把后台任务改绑到新账号，也不自动取消其业务或采集。

## 9. 本机数据、容量与权限

### 9.1 内容保护与脱敏

- 记录仅写入本客户端运行根下的 `.local/` 独立目录，建议 `.local/model-traces/`，使用独立 SQLite 元数据和受控正文存储；不混入聊天原库、分析结果或助手记忆。路径按客户端运行目录解析，禁止硬编码开发机路径，也不得使用设置中的“微信数据目录”或 `data_root_source.py` 的微信源数据路径。
- 正文可能包含真实聊天、资料和模型推断，应用只提供本机查看及用户主动复制；不得自动进入公开或私有代码仓库、发布包、普通备份上传、启动诊断或遥测。测试仅使用合成内容。
- API Key、Authorization、Cookie、内部控制令牌、URL 凭据及签名参数先清除，再进入诊断缓存、IPC、数据库、UI 或剪贴板。请求头采用明确允许列表，不按“除了几个敏感字段都保存”的方式采集；已知凭据值在错误正文等非结构化内容中也需屏蔽。无法安全处理的字段省略并注明。
- 每次尝试开始时绑定当次已知凭据的内存脱敏集合；配置轮换不得使旧尝试失去旧凭据的脱敏能力，尝试结束且相关缓冲处理完毕后释放。脱敏覆盖凭据跨网络分片、跨响应增量，以及结构化解析后等价的 JSON 转义和 URL 编码形式；不能仅逐片字符串替换。先完成脱敏，再计算保存配额、分块和截断，无法确认安全的尾片省略并说明原因。脱敏工作缓冲受第 9.2 节预算约束；不承诺自动识别聊天正文中任意未知机密。
- 不默认遮住全部聊天正文，否则无法核对实际提示词；设置说明明确告知这些正文会被保存。复制只响应用户主动操作，保持同等脱敏规则；记录库不作为可直接分享的诊断包。复制区域说明“保留期和清空不管理已复制到系统剪贴板或其他应用的内容”；不能凭普通复制成功宣称已禁止系统剪贴板历史或同步。
- 当前账号只能查询自身记录；后端按第 8.4 节校验身份和作用域，不能仅靠前端筛选。无账号的连接测试单独隔离，不提供跨账号合并正文视图。安全边界防止任意网页、不受信窗口或采集来源读取／伪造记录；目录按当前操作系统用户权限保护。微信账号作用域不等于操作系统用户隔离，不承诺抵御同一操作系统用户下拥有文件访问能力的进程或设备管理员。

### 9.2 保留期限、空间与缓冲预算

- 默认上限为最近 7 天、10,000 条实际尝试、500MiB 总占用，任一条件先满足即清理最早已结束采集的记录及附属事件，包括已停止采集或进程中断的记录。容量含正文、数据库、索引与附属文件；需实际回收空间，不能只删除数据库行后宣称空间已释放。
- 单次尝试的请求侧与响应侧已保存文本分别最多 16MiB，按脱敏后 UTF-8 字节计量。请求侧包括实际请求及额外保存的消息快照；响应侧包括原始事件、正文和应用处理结果。视图优先由同一份已脱敏内容派生，重复保存的表示按每份占用计入配额。达到上限后停止该侧正文追加，保留元数据及完整性标记；因上限无法保存应用结果正文时仍记录可得的处理状态。媒体占位计入文本配额，媒体二进制禁止保存。此限制不改变业务发送或接收的内容。
- 全局新增诊断缓冲中的内容字节总量上限建议 64MiB，覆盖所有采集进程的诊断快照、脱敏工作缓冲、发送队列、IPC 在途内容、接收队列及待写缓冲，不能让每个进程各占 64MiB。分配和释放需有统一可核对的预算；事件元数据与容器开销另设有界策略并报告峰值，不允许无界队列。业务本身必须持有的原内容不重复计为诊断缓冲，新增复制则计入。
- 正文按第 8.3 节分块传输和按需加载；查看界面只加载当前正文页的可见块与有界预读，不一次预取整条 16MiB 内容或整份任务历史。元数据、过程事件、占位与采集健康状态同样受有界条数／大小策略和全局空间约束，不能通过不计调用次数的事件无限增长。

### 9.3 采集故障与恢复

- 写入拥塞、磁盘满或达到容量且无法回收时，按第 4 节暂停规则保持业务运行，标“采集不完整／已暂停”及丢失计数，不能静默漏记后显示完整。不因故障增加模型请求、等待磁盘或挤占业务控制事件。
- 整次尝试的开始元数据也可能丢失。独立维护采集健康状态，展示受影响时间段、可确认的范围与丢失条数；不可确认时写“未知”。列表和汇总必须标记这一期间不完整，不能仅给已入库条目加标记。磁盘不可写时先在界面可查询的内存状态中保留故障；重启无法还原确切丢失量时明确说明。
- 故障检查建议按 1–30s 有上限退避，并可由用户手动请求检查存储；检查不调用模型、不补录暂停期间正文。恢复前确认存储可写、容量有余量且删除版本有效，再发布新采集版本。再次失败仍保持暂停，不生成无限增长的故障事件；关闭偏好优先于自动恢复。

### 9.4 删除与副本清理

- 清空、账号数据删除、助手会话删除或联系人记录移除时，按原删除操作的语义同步处理对应调用正文。明确删除某会话／联系人的本地内容时不得让副本残留；仅切换、隐藏或取消关注不等于删除。全账号清理必须覆盖所有相关调用库分区。
- 删除和保留期清理必须使迟到事件失效，清掉关联正文、索引、附件引用及待写缓冲；重启不能恢复已清理内容。对仍在运行的尝试如需清理，停止其诊断采集，不中断业务。
- 删除先持久化失效版本或删除标记，再清理正文及诊断存储产生的持久副本，包括数据库日志和临时文件。删除中崩溃后，重启先拒绝读取与追加，再完成未结束的清理，不从残余文件重建记录。失效标记无法持久化时不显示删除成功，当前运行拒绝访问并提示失败；重启不能被宣称已完成清理。仅在约定清理完成后显示成功，失败或待完成时明确提示；保证应用无法恢复已删内容并清理其管理的副本，不承诺磁盘取证级擦除。
- 保留期从记录创建时间计算。持续采集的长请求到期时同样结束诊断采集并清理，业务继续，不能无限豁免；其后续片段不得重建旧记录。
- 清空或作用域删除成功后，所有窗口立即撤销相关列表、详情和正文缓存；在途详情读取返回时复核删除版本，不能再次显示已删除内容。保留期清理命中正在查看的记录时，详情改为“记录已过期”，不继续保留其正文。

## 10. 性能与可靠性验收

以下为首版通过条件，使用固定合成数据和可控模拟服务验证。实施阶段先确定项目支持的 Windows 基准设备，记录 Windows 版本、CPU、内存、磁盘、应用／引擎／依赖版本和缓存条件，再按本节固定负载验收；数值调整须在验收前修订本稿并记录理由，不能在超标后仅称其为参考目标。

### 10.1 基准负载与测量口径

- 常规请求侧正文为 64KiB、响应侧为 256KiB，均按脱敏后 UTF-8 字节说明数据规模；明确消息数、响应事件数及固定分片节奏。模拟服务的请求内容、响应分片、输出间隔和重试条件在各组一致。
- 分别测量采集关闭、采集开启但面板关闭、采集开启且面板打开三种状态；每种状态预热 10 次后至少采样 100 次。分组轮换执行以减少缓存与运行时间漂移，p95 采用排序后第 ceil(0.95 × N) 个样本，并报告中位数、最大值和峰值新增内存。
- 列表／详情基准预置 10,000 条元数据，其中至少 100 条有上述常规正文，其余使用小正文；总量低于空间上限，测试期间只读，不新增采集记录。业务请求延迟基准另用各组一致的独立数据集，为全部预热和采样产生的记录留足条数及空间余量；不能复用已经达到条数上限的库。正常延迟样本期间不混入容量清理、暂停或磁盘故障，边界与故障测试另组报告。
- 列表和详情均分别测应用冷启动后的首次操作，以及清空应用级查询缓存后的重复操作；不要求清除操作系统文件缓存，但报告必须注明。首次启动不计入入口点击的耗时，应用就绪后才开始操作测量；不能用骨架屏出现代替内容可操作。

### 10.2 通过条件

| 指标 | 起止点与条件 | 通过条件 |
| --- | --- | --- |
| 首批列表 | 打开入口到首批至多 50 条元数据可见、可选择及筛选 | 重复操作至少 100 次，p95 ≤ 500ms；冷启动首次操作独立验证 ≤ 500ms |
| 常规详情 | 选中记录到概览及当前内容页首块实际内容可查看、可操作 | 重复操作至少 100 次，p95 ≤ 1s；冷启动首次详情独立验证 ≤ 1s |
| 业务首段正文延迟增量 | 从相同业务请求触发点到业务消费者收到首段可见正文；每个固定场景比较开启与关闭状态的配对差值 | 面板关闭及打开两组新增延迟 p95 均 ≤ 50ms |
| 业务完成延迟增量 | 从同一业务触发点到业务响应完整交付，比较同一场景的配对差值 | 面板关闭及打开两组新增延迟 p95 均 ≤ 50ms |
| 流式诊断刷新 | 正常存储下，新增已脱敏内容到诊断界面显示 | 合并更新间隔 200–500ms；正常结束后 1s 内刷新剩余内容 |
| 批量落盘 | 正常存储下，诊断内容入队到持久写入完成 | 最长等待 ≤ 1s；正常结束后 1s 内处理尾部，失败时标缺口，不阻塞业务完成 |

首段和完成延迟测量业务消费者，不以诊断面板自身节流后的更新时间代替。若采用中继，三组保持相同路由；另与改造前的直接传输基准比较并报告常驻中继开销，不能借三组共同承担中继开销来宣称没有架构成本。

### 10.3 边界、并发与不干扰业务

- 开关关闭时不为诊断额外构造、序列化或落盘请求／响应正文；仅做轻量状态判断。查看历史可按需读取已保存正文，不启动请求捕获。业务本身正常构造和处理请求。
- 三种状态下，相同模拟模型请求的正文、参数、业务结果、既有重试次数及原因一致；路由所需的本机控制标识不进入 provider 请求。诊断采集、故障检查及界面操作均不得增加模型请求。
- 单独验证请求侧和响应侧各接近 16MiB 及超过上限的内容，含单个超大协议事件；按分块显示，截断和缺口清楚。大正文到首块可查看 ≤ 1s，不要求一次呈现全量正文；浏览时聊天输入和面板关闭仍可操作。
- 至少同时运行 10 个不同联系人、不同助手会话的任务，分别验证常规负载及大正文压力。结果无串线、无重复，诊断内容缓冲符合 64MiB 总预算；压力超预算时可按约定暂停并标缺口，不能无限排队或阻塞业务。数字是验收负载，不增加业务并发限制。
- 慢消费者、传输断线、写入拥塞、空间不足及故障解除单独测试，不纳入正常延迟统计。强制退出允许丢失尚未落盘内容，恢复后须明确不完整或结果未知。流式结束、启停和删除发生在刷新／落盘边界附近时，完整性与失效版本仍正确。
- 性能报告列出各组数据、未通过项及原因，不能只报告落盘耗时或平均值；采集、存储、列表与详情的新增内存分开说明，压力结束后诊断队列回到稳定水平。

## 11. 验收场景

全部使用合成聊天和可控模拟服务；最后以用户已配置的服务做最小连接兼容验证，不能用真实聊天填充测试样本。

| A25 | 固定性能基准 | 第 10 节数据集、三种状态、样本量、冷／缓存口径及 p95 测量可复现；正常和压力／故障分组报告，达成阈值与缓冲预算；中继常驻开销另行披露 |
| A26 | 采集验证门槛 | 固定引擎与运行包一致；有支持矩阵及合成收包证据；核心助手路径不可采集时记录缺口，不冻结完整工期或标完成；依赖升级重新验证受影响路径 |

## 12. 实施顺序与完成标准

1. **验证采集边界**：按第 8.2 节用合成数据贯通连接器与 OpenCode provider 层，输出支持矩阵，证明最终请求、原始响应、并发关联和启停连续性可获得；确定 Laya 批次与 probe 边界、认证方案及跨进程预算。未通过路径保留明确缺口。
2. **冻结核心方案与验收基准**：验证通过后，复核当前源码和运行包，登记首版核心范围、采集方案、基准设备、默认数值及工期估算。按第 1 节将体验增强列为后续项；核心采集和安全要求不能被默认为可选。
3. **建立记录基础**：统一诊断任务与业务执行标识、启停／故障状态、脱敏、分块传输、独立存储、容量限制和安全查询，覆盖全部可达业务入口。
4. **实现核心查看界面**：设置、聊天快捷入口、独立历史入口、独立桌面记录窗口、列表和四个详情页，支持基本筛选、实时更新、复制及清理；核心版使用默认窗口大小与跟随范围。
5. **完成端到端验收**：逐项执行第 11 节，报告第 10 节性能与故障结果，补齐打包清单及文档；先完成针对性测试，再执行仓库要求的完整检查。增强项交付时补验对应交互，不阻止已满足全部核心条件的版本交付。

完整完成标准为：第 7 节全部可达来源及支持矩阵中的适用组合通过核心验收，安全与生命周期条件通过，性能达到冻结指标，运行包包含所需模块。可单独标注已验证的阶段成果，但存在核心路径缺口时不能声称本需求已完成或已全量覆盖。只显示最后一段回答、只打印控制台日志、只记录应用提交参数，或遗漏助手引擎内部调用，均不满足核心完成标准。
