# 知己分析多窗口与关系记忆迁移需求

产品：知己微信助手 · Zhiji WeChat Assistant。更新日期：2026-10-10。品牌名称按[当前约定](branding.md)更新。

> 2026-10-12 更新：页签、统一分析按钮、好友概述、人格分析与聊天分析的新需求见 [知己分析 v2](friend-analysis-v2-requirements.md)。本次评审确认先出近期概述、全历史分段提取证据、AI 与人工修正独立、人格描述为主；栏目、分析入口、类型与议题观点边界等冲突条目以该文档为准，其余规则继续有效。

状态更新（2026-11-02）：**原 A–D 阶段主体已在本地 `dev` 实现**，包括固定联系人的独立多窗口、可编辑关系记忆、全历史建档、关系趋势、联系目标／本人资料及助手资料接入。页签、分析入口和人格展示已由 [v2 需求](friend-analysis-v2-requirements.md)及后续实现演进，当前操作见[知己分析说明](friend-analysis.md)。

本文保留原交付范围和验收标准，不表示所有真实数据、模型质量与发行环境组合已经验收。当前共同验收事项见[需求待办清单](requirements-todo.md#validation)；下文“三个栏目”等旧布局不再作为待实现项。

本轮交付要点：

- 本轮交付阶段 A–D 全部内容，包括联系目标、自身资料及记忆接入建议。
- 记忆候选不设数量上限，改为严格查重与“补充”合并；记忆使用固定标签，可按标签或时间线排列。
- 关系趋势可按小时、天、周、月、年切换（默认按月），可把某一天按分钟展开；视图分为总览、消息条数、发言轮次、文字量、回复时间，每个视图只显示自己的数据；粒度与视图各窗口同步。
- 首次建档覆盖全部可读历史，开始前显示预估；之后打开窗口时自动增量更新。打开窗口时自动读取本地聊天历史。
- 不按资料类别排除对方明确提供的信息；资料由用户在本机管理，提取保留准确性、归因与数据隔离要求。
- 撤回或核对不上的原文只做标注，记忆可用性不变。
- 群聊不显示“知己分析”按钮，现有群画像本轮暂时隐藏。
- 未保存编辑自动暂存，关闭窗口与退出应用不再弹窗。
- 证据先在窗口内看上下文，“在聊天中定位”直接跳转主聊天。
- 界面整体简约，设计逻辑贴近微信电脑版。

## 1. 产品目标与范围选择

让用户在一个独立空间中理解朋友、回顾共同经历、维护可靠记忆，并把自己认可的资料用于交流建议。默认普通好友关系，不预设恋爱或追求目的。

“知己分析”窗口固定三个栏目，依次为 **关系记忆、好友分析、关系趋势**。关系记忆承载已知资料与共同经历，好友分析承载对聊天表现的解读，关系趋势展示交流随时间的变化。好友分析先复用已有画像能力，不在本轮重做评分算法。

## 3. 知己分析多窗口与简洁界面

### 3.1 打开与切换

- 主聊天按钮由“人物画像”改名“知己分析”，位置保持在“聊天记录”左侧；同步更新按钮提示、可访问名称与相关打开入口。窗口标题建议为“联系人名称 · 知己分析”，正文不重复堆叠产品名与栏目介绍。
- 点击打开或聚焦目标联系人的窗口，不扩宽、缩窄或替换主聊天内容，不收起聊天助手。无需在分析窗口里再增加联系人列表或第二套聊天导航。
- 窗口顶部只保留头像与联系人名称，不显示账号标识或长技术 ID。所有请求绑定该窗口自己的账号、会话及模型来源，并校验请求代次，不读取主窗口的临时选择；切换模型后旧响应不得覆盖新视图。
- A 的分析打开后，主聊天切到 B，A 窗口保持原联系人、页签、滚动和草稿。在 B 的聊天点击“知己分析”时，另开 B 窗口；A、B 可以同时存在并独立移动，不复用 A 的窗口承载 B。
- 同一账号同一联系人重复点击只聚焦已有窗口；最小化时恢复，不重置页签、编辑内容和任务。联系人同名也按稳定身份区分，不能共用窗口。
- 每个窗口独立编辑。打开或关闭 B 不影响 A 的草稿。未保存的编辑自动暂存，按账号、联系人与条目保存在账号数据库中；关闭窗口不弹确认，重新打开时恢复草稿，并标明“未保存”。清除账号时草稿一并删除。
- 关闭单个窗口前须完成最新草稿的持久化；暂存失败时保留窗口与编辑内容，提示重试，不能静默关闭丢失文字。暂存不等于保存或确认记忆，草稿不进入助手上下文；正式保存或明确放弃后清除相应草稿。
- 暂存带编辑序号与草稿代次，迟到的旧请求不能覆盖新内容，或在正式保存、放弃后复活草稿。账号共用设置的编辑草稿还须区分编辑窗口；A、B 的未提交内容分别保留，正式保存仍按资料版本处理冲突。
- 关闭一个分析窗口不关闭其他窗口、不停止它或其他人的已提交任务。不能以新增窗口为由隐式回收旧窗口；本轮无需增加集中对比页、排名或自动平铺功能。
- 账号发生切换、注销或清除时，属于旧账号的所有分析窗口立即遮蔽旧资料并禁用操作，提示重新从聊天打开；旧事件不能重新显示资料。清除操作同步到所有视图。
- 群聊会话不显示“知己分析”按钮。现有群整体与群成员画像本轮暂时隐藏入口，数据与缓存保留，不删除；群分析以后单独立项。记忆只从个人私聊提取，不把群聊中的发言合并进个人档案。

### 3.2 布局与生命周期

窗口内容从上到下为：紧凑的人物标题与必要操作 → 三个栏目 → 当前页内容。证据、任务详情和设置按需打开，不占常驻侧栏。默认进入“关系记忆”；已有窗口重新聚焦时保持当前页。

| 区域 | 主要内容 |
| --- | --- |
| 关系记忆 | 对方明确提供的背景、经历、性格、爱好、偏好、边界与共同事件；按标签分组或按时间线排列；确认、编辑、删除与回查来源。自己的背景留在账号设置 |
| 好友分析 | 简短分析摘要、沟通方式、互动表现、常聊话题及“我的观察”；已有互动评分（原“好感度”）与 MBTI 倾向收在折叠的已有分析详情中，有来源与推测标记 |
| 关系趋势 | 联系频率、双方参与、回复节奏等随时间的变化；可按小时、天、周、月、年切换并按分钟展开某一天；保留日期范围与缺失提示，详见第 6.2 节 |

- 建议初始尺寸约 960 × 760，按屏幕可用区域缩放；小屏使用单列、页面滚动，按钮不被裁切。不因无法在主窗口右侧增加固定宽度而拒绝打开。
- 保存窗口位置与尺寸，恢复前校验当前显示器可用区域；断开外接屏后仍可访问。本轮不默认置顶。
- 新窗口采用适当错位，避免完全盖住原窗口；支持系统自带的并排布局。各窗口位置与大小互不覆盖。
- 关闭分析窗口只关闭展示；已提交的建档或分析由后台继续保存。重新打开读取真实任务状态和结果，不为恢复展示重新发起任务。
- 主聊天与助手的草稿、滚动位置、正在生成的任务均保留。真正退出应用时才按既有退出流程结束后台工作；重启显示“已中断，可继续”，不假装关机期间持续运行。
- 保持当前桌面的退出语义：用户关闭主窗口时，先暂存所有分析窗口的草稿，再同步关闭这些窗口并执行原应用退出流程，不逐个弹出确认。暂存失败时才提示，并允许取消退出。不能因为新增窗口尚存而遗留后端已停止的孤立界面。
- 普通浏览器入口不必实现独立桌面窗口；应说明需桌面客户端，不遗留看似可用却无响应的按钮。

### 3.3 简洁界面规则

- 整体风格简约，设计逻辑贴近微信电脑版：浅色模式采用白底列表与浅灰分隔，深色模式沿用主界面主题；栏目切换像微信的简单页签，微信绿只用于主操作。沿用主界面已有的字体、间距、控件与颜色，不强制改变用户的主题。没有必要的元素不出现。
- 一级导航只有“关系记忆 / 好友分析 / 关系趋势”，不额外增加概览、背景、联系目标、任务中心等栏目；已有概览内容分配到相应页面。
- 默认展示有内容、能帮助判断的信息。没有数据的维度不排列成一墙“暂无”；整页无内容时只给一句说明与一个相关操作。样本不足、过期或来源缺失等会影响判断的信息必须保留。
- 每页突出一个主操作，如“更新记忆”或“更新分析”；编辑、删除、清空、设置等放条目操作或更多菜单。保留可理解的操作名称，不为省字把所有按钮变成难认的图标。
- 证据、详细统计口径、模型信息、覆盖明细和任务过程默认折叠；页面只保留必要的“待确认 / 推测 / 待更新”等短标记，避免重复说明、长提示和技术参数。
- 任务运行时显示一行简短进度，点击才展开过程；成功后的状态不长期占大块区域。失败展示简短原因与重试入口。
- 不使用大块装饰、卡片墙、重复标题、宣传语或大量徽章争夺注意力。不同联系人的同一栏目使用一致布局，便于并排查看。
- 简洁不能抹掉事实与推测、AI 与人工记录的区别，也不能隐藏会影响使用的错误、未保存状态和数据范围。相同说明优先集中到可展开的“依据”或“说明”里。

## 4. 可编辑的长期记忆

### 4.1 记录内容与归属

每条记忆最少保存：唯一 ID、账号与联系人身份、标签（可多个）、内容、状态、来源类型、首次提及时间、创建与修改时间、版本；适用时保存事件时间或有效区间、证据列表、生成批次和模型来源。

- 标签使用固定集合：基本信息、经历、性格、爱好、偏好与忌口、边界、共同事件。一条记忆可以有多个标签，AI 提取时自动打标签，用户可以修改。本轮不提供自定义标签。
- “性格”标签只收对方自述或在原文中明确表现的内容，例如“我是急性子”；模型对性格的综合判断放在好友分析，不进关系记忆。
- 共同事件不得只因用户提出邀请就认定已经发生。
- 关系记忆提供两种排列：按标签分组（默认）和按时间线。时间线优先使用事件时间，没有事件时间时使用首次提及时间，并区分两者。
- 状态：待确认、已确认、已否定。界面上的“忽略”对应已否定，已否定的记录不在默认列表中显示。删除另行记录排除信息，不以普通“待确认”状态隐藏。
- 来源：AI 提取或用户记录。用户新增默认已确认并标“用户记录”；无聊天证据时写明“未关联原文”。
- AI 只能新增候选，不自动确认，不覆盖用户修改，也不把同名联系人合并。用户确认表示认可这条记录，不宣称外部核实。
- 证据区分本人发言、用户发言、引用、转发与未知说话人。关于朋友自身的自动事实需要朋友本人的有效正文；共同事件按双方原话核对参与者、时间和是否成行。
- 目标、个人备注、AI 回答、回复草稿、摘要及人工猜测不能冒充微信原文。媒体只有占位时不得提取其视听内容。
- 不按资料类别排除对方明确提供的信息：对方自述的健康、饮食、信仰、感情等内容与其他内容同等提取，保留归因与证据。对方没有明说、由模型推测的内容不进关系记忆。好友分析的推测限于本轮保留的既有画像与沟通互动观察；本条不增加对未自述的健康状况、信仰等敏感属性的推断能力。
- 既有 MBTI 倾向继续作为旧画像推测展示，不自动转成已确认事实或本人自述。

### 4.2 操作与冲突

- 面向用户的操作只有：候选“确认 / 忽略”，已确认记录“编辑 / 删除”，以及手动新增和只清空当前联系人的记忆。候选支持批量确认或忽略（按标签或全选）。删除或清空前说明操作范围；不删除微信原记录、主动助手历史、联系人或目标。
- 修改已有事实时记录新版本，不能把原证据显示为直接支持修改后所有文字；必要时改为“用户修正”，保留证据供核对。
- 已确认与已否定记录不会被重跑覆盖。相互矛盾的新说法进入待处理冲突，可选择保留原记录、采用新说法或分别注明不同有效时期，不让模型自行覆盖。
- 建档不设候选数量上限，以严格查重控制数量。重复记忆既增加审核负担，也浪费建议的上下文。
  - 候选入库前，与该联系人的已有记忆比较，包括待确认、已确认记录和排除记录。同一批候选之间先合并。
  - 与已有记录完全重复或明确判定语义相同的候选不重复展示，保留查重关联供排错；同义合并不能掩盖新细节、时间变化或矛盾。
  - 说的是同一件事、但带有新细节的候选，挂在原记录下作为“补充”，确认后合并为原记录的新版本，并保留双方证据。
  - 语义查重可由模型对照检索出的已有记忆完成；标签用于缩小候选范围，但不能因标签不同就跳过同义内容。记忆较多时分批检索比较，不把全部记忆无界塞入请求。无法确定重复、补充还是冲突时保留待核对关系，不自动丢弃或合并。
- 同批重试、无变化重跑通过稳定提案键与规范化内容校验保证幂等。删除与忽略生成排除记录，阻止相同或明确判定语义相同的提案再次出现；语义判定以包含同义、否定、时间变化、新细节和跨标签案例的测试集验收，不承诺模型对任意表述完全准确。
- 编辑、删除、忽略、清空均递增记忆版本；旧任务只能成为过期结果，不能复活旧记录。即便当前列表为空，清空也要使在途提取失效。
- 编辑采用版本校验。发现另一个操作已修改同一记录，提示冲突并保留当前编辑草稿，不悄悄覆盖。
- “清空记忆”是清理结构化记录，并不等于系统彻底忘记仍存在的聊天原文；界面明确说明。不在本轮增加彻底抹除联系人全部资料的功能。

### 4.3 证据查看

- 每条自动候选至少关联一条有效原消息，并可在窗口内查看说话人、时间、原文及必要上下文。证据 ID 存在还不等于内容支持结论，输出校验应拒绝明显不受证据支持的内容。
- 老消息不受聊天页最近加载条数限制。点开证据时，在分析窗口内直接显示原文及前后若干条上下文（建议各 5 条），大多数核对不必离开窗口。
- “在聊天中定位”是次要操作：主聊天按完整账号、会话与消息身份直接跳转。现有 `jumpToHistory` 依赖主聊天当前作用域，实现时先通过受控入口校验账号并切换到目标会话，再定位消息；不能直接向当前会话传入另一个联系人的游标。只有主聊天存在未发送草稿时才先确认。分析窗口保持原联系人，旧账号窗口不得借此恢复访问。
- 证据保存消息身份与内容哈希，不依赖投影行永久存在。现有 `context_begin(reset=True)` 在来源变化、消息内容变化或回退时会删除该联系人的全部投影消息与摘要。历史重新读取后，按“消息 ID + 内容哈希”自动重新核对，只把对不上的证据标出来，不要求用户逐条重验。
- 对方撤回或原文核对不上时，只标注“原文已撤回”或“原文已变化”；记忆的状态与可用性不变，包括用于建议。
- 只有来源明确报告撤回或有可核验的内容变化时才使用上述原因；无法定位、历史未就绪或来源身份变化分别标注，不把“找不到”推断为“撤回”。重新核对仍须先匹配账号、联系人和来源身份，不能仅凭相同消息 ID 与哈希跨来源重新绑定。
- 日期未知、原文截断、消息不可读、来源变更分别显示，不补造原文或相对日期。
- 窗口先显示记忆列表，点击才读取证据；长列表分页，建议每页 50 条。媒体只展示类型与已存在的可用入口，不自动加载原件或播放。

## 5. 历史建档与可见进度

### 5.1 触发、覆盖与持久化

- 窗口涉及四类任务，各自显示进度，不能合并为同一个进度：
  - **读取聊天历史**：本地读取微信记录，写入受管历史投影，不调用模型。现有投影是按需建立的，从未在助手中打开过的联系人可能还没有数据。打开分析窗口时，如果该联系人尚未导入或有新消息，自动启动读取，复用现有 `ContextProjection.prepare`。
  - **建立记忆（全量）**：只能由用户点击触发，覆盖本项目当前可读的全部历史。开始前显示预计分段数与耗时范围；分段数依据已读取数据和实际预算，耗时依据可用的同模型测量。没有足够测量时显示“耗时暂无法估算”，首批完成后更新，不为预估额外启动一次提取。不批量给所有联系人建档。
  - **更新记忆（增量）**：建档完成后，每次打开该联系人的分析窗口时，自动处理上次高水位之后的新消息。不在后台随新消息自动运行；保留“更新记忆”按钮供手动触发。
  - **画像统计**：沿用既有触发规则。
- 打开窗口不会自动启动全量建档。
- 打开或从主聊天再次点击聚焦已有窗口时，先刷新并等待该联系人的共享历史读取完成（复用 `prepare(refresh=True)` 与 `wait_ready` 的语义），再按已提交检查点判断是否有增量；普通切页或系统焦点变化不触发。没有新增内容不调用模型，同一联系人已有活动任务时复用任务。
- 停止、失败或中断的记忆任务优先显示“重试 / 继续”，再次打开窗口不能绕过它另开自动任务。检查点同时绑定来源、投影代次、提取版本、消息身份与内容哈希，记录连续成功提交的范围，不能只比较消息序号或最大时间、跳过未提交批次。历史回填、内容变更或来源重建后先核对覆盖。能够可靠识别的未覆盖片段按增量处理；无法证明检查点有效时提示重新建档，由用户触发，不自动变成全量扫描。
- 记忆提取直接复用现有受管历史投影；按模型实际配置与输出预算分段，不能因用户宣称上下文很大就把全部历史无界塞入一次请求。
- 快照固定来源范围、记忆版本、提取规则与模型版本。新增聊天可以标为“有新内容待更新”；基于旧高水位的合法批次可以完成，但不能冒称已覆盖新消息。原文改写、账号来源变化、用户纠错或清空须按影响失效。
- 检查点按批次保存；批次候选和覆盖进度原子提交。最终记忆保留待确认状态；任务详情中的临时候选要与已入库候选分开标识。
- 同联系人重复点击返回已有活动任务。请求超时后先查任务状态，重试使用请求 ID 去重；失败保留有效检查点，继续时重新校验，不重复插入已保存候选。
- 应用重启后恢复已完成检查点，用户点击“继续”才启动中断任务。本轮不承诺持久后台服务或自动补跑离线历史。

### 5.2 用户能看到什么

任务摘要只占一行，优先显示当前阶段与已完成消息 / 本次可处理消息，例如“提取记忆 · 320 / 860 条”。未知总量显示“正在统计”，不编百分比或剩余时间；联系人已经在窗口标题出现时不再重复。

展开任务详情后展示：任务类型、正在读取的片段范围、已完成分段 / 总分段、覆盖日期、耗时、最后活动时间、当前步骤（准备、读取、提取、校验证据、保存、等待重试）、尝试次数、错误说明、已保存检查点、候选数量及可展开的原文来源。展示处理对象和步骤，不要求暴露模型内部思考过程。

- 当前没有模型输出时，明确显示“等待模型返回”，不要用动画表示已经生成了内容。
- 提供“停止”与失败或中断后的“重试 / 继续”。停止只作用于这一任务，保留已完成检查点，不等同于删除记忆。
- 切换主聊天、打开另一个人的窗口或关闭某个分析窗口，都不取消已提交任务；任务完成后仅更新所属联系人的视图。A、B 同时处理时各自显示进度，结果不得串入另一窗口。
- 队列与并发使用现有模型运行时能力及其限制。建档与打开窗口触发的增量更新，优先级低于用户主动提问和自动建议，不得饿死它们。具体并发数由实现测量决定，不另启动一套无约束模型客户端。

## 6. 好友分析、关系趋势与建议接入

### 6.1 好友分析与人工观察

好友分析首先呈现简短摘要与有依据的沟通观察，不重复罗列关系记忆里的背景资料；需要时引用对应记忆或原文。“我的观察”与已有 AI 画像分别保存，可填写一句话判断和依据备注；可选关联既有互动维度。模型重算不能覆盖人工记录，人工观察默认不进入已确认事实库。

本轮保留已有画像算法及来源、覆盖范围标记，不叠加另一个好感度总分。继承的好感度与 MBTI 倾向不占页面主视觉，放按需展开的已有分析详情。界面上的“好感度”改称“互动评分”，其评分方法已知存在问题，重新设计列入后续。不把其历史缓存删除或改称客观事实。新的沟通维度生成和模型关系复盘属于后续，基础关系趋势按下节纳入本次范围。没有依据时显示未知，不用 0 分或 50 分补齐。

### 6.2 关系趋势

关系趋势栏目已由用户确认。以下为首版指标与时间窗口的建议口径，可复用旧项目的确定性统计，不依赖模型先完成整份画像，也不默认额外请求 AI 生成长篇解读。

- 展示一张随视图切换的柱状图和该视图自己的卡片：总览汇总各项（选中时间超过一天时另有联系天数和双方都发言天数）；消息条数附类型分布；发言轮次（同一方连续发的多条算一轮，不受拆条习惯影响）附平均每轮条数和谁先开聊；文字量（只数文字，图片、语音、表情包另列条数，不折算）附平均每条字数；回复时间（我和对方并排画平均值，纵轴默认按实际时长，可开启对数刻度）附中位数、最久一次和快慢分布。回复从对方发完第一串消息算起，追问不重新计时，隔 8 小时以上算开聊而非回复。点击柱子查看该周期，拖动框选或 Shift+点击可选一段时间，卡片按整段汇总并给出日均。指标使用原始次数、天数、比例或时长，不默认转换成综合“互动指数”或好感度分数。
- 时间粒度由用户在小时、天、周、月、年之间切换，默认按月；分钟只用于展开某一天，避免全历史数百万根空柱。各粒度都覆盖从可读历史第一条消息到现在的全部聊天，不截取最近一段；滚轮以鼠标位置为中心缩放柱宽（每种粒度分别记住），Shift+滚轮、触控板或滚动条左右移动，框选拖到边缘时自动滚动，打开时停在最近的周期。粒度与口径在所有打开的分析窗口间同步，并记住上次选择，保证并排时口径一致。
- 不做“本期对上期”的自动对比，用户点击任意柱子自行查看；默认选中最近一个有消息的周期。当前未结束的周期在图上标“进行中”。
- 明确截止时间、时区与可读历史覆盖。历史覆盖或样本量不同需可见，不根据谁的消息多就判断谁的关系更好。
- 先映射本项目的发送方向、时间、系统消息与缺口，再复用 `calculate_relationship_metrics` 的方向、时间校验与回复节奏规则，把其固定的 28 天窗口改为按粒度参数化。按双方连续消息块计算回复节奏；未知方向或时间、无法判定顺序的消息不产生推测的回复时长或开聊归属。
- 所有周期采用同一口径。缺失历史、样本不足时显示“数据不足”及可展开原因；没有完整覆盖不能把缺失记成零，也不能画成关系下降。确认覆盖内确实没有交流时可显示零。
- 近期数据变化可以触发本地统计刷新；更新使用数据版本去重。打开多个窗口不重复导入同一份历史，不重复触发模型建档。
- 不把慢回复直接解读为疏远或隐藏情绪，不把频率变化写成对方内心的确定结论。解释以实际行为和时间范围为限；详细计算说明放折叠区。
- 本轮最终交付须包含可工作的基础趋势，不能只有“规划中”页面。阶段开发可有简短未完成状态，但不得作为最终验收。

### 6.3 联系目标与自己的资料

- 联系人目标使用自由文本，提供可选起点：自然交流、保持联系、了解近况、讨论具体事项、安排见面；默认“自然交流”，不预选约会。
- 保存本联系人的目标说明；目标是用户希望的方向，不代表对方同意或关系状态。
- 联系目标从窗口“更多 / 设置”进入，不设第四个栏目、不常驻大卡片。关系记忆中的“人物背景”属于对方；自己的背景与风格属于账号设置，两者不混排。
- 自身背景、偏好表达风格放本账号共用设置，在分析窗口的设置中提供快捷入口。“共用”指该账号内的联系人，不自动跨账号复制。
- 目标与自己的资料不写入朋友的事实表。示例和测试使用虚构内容，不读取真实私人资料填入文档。

### 6.4 接入现有助手

- 阶段 D 将已确认记忆、当前联系人目标、本账号自身资料与风格作为独立且有标记的上下文段，供主动助手与自动三条建议复用。
- 只选取当前联系人且相关的已确认记忆，并明确上下文覆盖范围。未确认、已忽略、已删除的记录不得当成事实注入。已确认记录即使原文撤回或核对不上，仍可选入上下文，但必须一并传入“用户已确认”和当前证据状态，不能伪装成仍可核验的原文或编造引文。
- 注入时同一事实只出现一次；记忆较多时按相关性与上下文预算选择，不整表塞入。
- 用户本轮明确要求优先于一般风格和目标；任何措辞要求都不能把猜测写成经历、把目标写成对方意愿。回复不编造用户经历、可用时间、承诺或共同活动。
- 修改目标、风格或记忆后，现有自动候选标为过期，并使使用旧资料的生成结果失效。保留常驻“重新生成”，不因为每次编辑就自动请求模型。
- 已确认记忆的证据状态变化也更新助手上下文版本，保证后续请求得到最新标记；不因此自动取消用户确认或删除记忆。
- 模型会话和缓存的复用必须包含资料版本；下一轮不能继续偷偷使用改前的记忆。主动助手已保存的历史问答可以保留，但不回灌成事实；旧版本生成的回答应标明资料已更新。
- 资料版本须进入原生模型会话绑定、请求快照与结果提交检查。仅更新资料文件或 `contextRevision` 不足以清除模型会话里已经读取的旧资料；版本变化后应换代原生会话或可靠移除旧资料上下文，界面的历史问答仍保留。
- 保留既有行为：自动建议仍按联系人开启、只生成三条可复制结果、不自动发微信、不覆盖草稿、不写入主动助手问答。切换聊天时主动助手继续后台生成。

| `bridge/advisor_service.py`、`bridge/advisor_auto_reply.py`、`electron/advisor-runtime.ts` | 资料版本进入任务快照与运行时失效逻辑，复用已配置模型连接 |

| `scripts/stage-real-client.py` 与既有清除账号流程 | 新模块进入打包清单；新任务和数据纳入账号清理、排空与迟到写保护 |

- 证据身份至少包含账号、来源指纹、会话、消息 ID 与内容版本；保存可用的定位游标。`seq` 只是当前投影顺序，不能作为永久证据身份。当前微信消息 ID 也不是跨数据库迁移永远稳定的 server ID。
- 历史投影重建换代时，保留用户确认和人工资料；重新读取完成后，按消息 ID 与内容哈希自动重新核对证据，只标出对不上的。旧任务按版本失效，不静默删除人工记录。
- 画像的“重置分析”不得顺带清掉人工记忆与目标；“清除账号”则须排空新任务并清除该账号的派生资料，晚到结果不能重新创建文件。
- 新窗口只加载受信任的本地应用页面，不拿 API 密钥、不开放任意文件或网络执行能力。IPC 和证据接口在服务端复核作用域，不能仅凭前端联系人参数读取别人的资料。
- 新窗口与主窗口共享缓存时使用明确的数据持有者或按条更新，不各自把整份旧内存快照写回 localStorage；重置、修改和账号清除事件要同步到所有打开的视图。
- 窗口去重按账号、会话与人物身份；模型来源属于窗口内部的数据版本，换模型不另外创建同一个人的窗口。每个窗口持有自己的页签、筛选、草稿、请求控制器和事件订阅，不能复用全局当前联系人；销毁只解除该窗口订阅，不释放其他窗口或任务仍在使用的账号资源。
- 自身资料与表达风格是账号共用配置，在 A 窗口修改后应同步相关版本到 B 等窗口及助手；仍保留各窗口未提交的编辑，用版本冲突处理而非静默覆盖。
- 实际数据迁移单独立项：先备份并明确旧联系人、原消息与新身份映射，再逐条核验，不按名字匹配，不复制旧数据库覆盖现库。
